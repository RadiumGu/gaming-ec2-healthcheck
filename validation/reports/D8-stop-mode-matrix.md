# 验证报告 D8 —— 停止模式矩阵：推翻 D4 的恢复段结论

执行时间：2026-09-17 06:58–07:15 UTC
被测实例：`i-TARGET00000000002` m7i.large / 203.0.113.30 / AL2023 x86 / ap-northeast-1a
编排：`design/scripts/stop_matrix.py`（本轮新写）
原始数据：`validation/raw/D8/healthy-matrix.ndjson`、`panicked-matrix.ndjson`

## 为什么重做

第一轮 D4 报了「挂死实例 force stop 257.2 s，健康实例 16.8 s，差 15.3 倍」，
并据此给客户的结论是「自建恢复路径的收益全在检测段，恢复段没有改善」。
这个结论建立在三个错误上：

1. **机制解释错了。** `Force=True` **不跳过**优雅关机。`StopInstances` API 参考原文：
   「The instance **will first attempt a graceful shutdown** ... If the graceful shutdown
   fails to complete **within the timeout period**, the instance shuts down forcibly」。
   真正绕过 OS 关机流程的参数是 **`SkipOsShutdown=True`**，第一轮完全没用。
2. **n=1。** 257 s 与 16.8 s 各只测一次，却报了一个倍数比值。
3. **`running → app_ready` 的 89.7 s / 121.8 s 是自己的缺陷造成的**（见下）。

---

## 结果一：挂死 guest 上，停止参数决定一切

| 组 | n | min | median | max | 原始值 |
|---|---|---|---|---|---|
| `panicked/force` | 2 | 250.318 | **252.197** | 254.076 | 250.318, 254.076 |
| `panicked/skip_os` | 2 | 10.838 | **11.453** | 12.067 | 10.838, 12.067 |

**22 倍差异，两组各自都很紧**（force 组极差 3.8 s，skip_os 组极差 1.2 s）。
`force` 组的 252.2 s **复现了第一轮的 257.2 s（差 2%）**，
说明那个数字本身没测错 —— 错的是对它的归因。

### 归属判定（最终）

**257 秒不是「挂死 guest 的固有代价」，而是用错 API 参数的代价。**

`Force=True` 对一个内核已 panic、永远完不成关机流程的实例，必须把优雅关机的
超时整个走完（实测约 250–254 秒，这个值稳定，像是一个固定超时常量）。
换成 `SkipOsShutdown=True` 直接绕过 OS 关机流程，10.8–12.1 秒就停下来了 ——
落在健康 guest 的同一个带内。

---

## 结果二：健康 guest 上四种模式无法区分

| 组 | n | min | median | max | 原始值 |
|---|---|---|---|---|---|
| `healthy/plain` | 3 | 14.171 | 16.357 | 18.207 | 16.357, 14.171, 18.207 |
| `healthy/force` | 3 | 16.308 | 18.621 | 20.548 | 18.621, 20.548, 16.308 |
| `healthy/skip_os` | 3 | 8.688 | 11.996 | 17.315 | 11.996, 8.688, 17.315 |
| `healthy/force_skip` | 3 | 5.467 | 10.969 | 17.780 | 10.969, 5.467, 17.780 |

`skip_os` / `force_skip` 的中位数略低，但**四组范围全部重叠**
（`skip_os` 最大 17.3 > `plain` 最小 14.2），n=3 **不足以断言差异**。
诚实的说法是：**健康 guest 上四种模式无法区分，都在 5–21 秒带内。**

这本身印证了机制解释：健康 guest 能走完优雅关机，从来碰不到那个超时，
所以 `Force` 传不传没区别。

> **这句原文写的是「差异只在「关不掉的 guest」上才暴露出来」，不够准确，已由 D11 修正。**
> 差异在「**应用不响应 `SIGTERM`**」时就暴露，不必等到内核死掉：
> D11 实测「应用冻死但 OS 完全正常」这一档，普通 stop **103.4 s** 对 `SkipOsShutdown` **5.7 s**，
> **18.2 倍** —— 而那台实例是关得掉的。约 90 秒来自 systemd `TimeoutStopSec` 默认值。
> 本报告只测了健康与挂死两个极端，缺了中间这一档，见 `D11-stop-hung-app.md`。

## 结果三：`running → app_ready` 只要 7 秒，旧数字是自己的缺陷

| | 值 |
|---|---|
| 本轮实测 | **中位数 7.014 s**，n=12（healthy 组），范围 6.010–7.097 |
| panicked 组同一段 | 7.016–8.013 s，与 healthy 组一致 |
| 第一轮 D4 / D4b 记录 | 89.7 s / 121.8 s，标为「上界」 |

第一轮的 `recovery_orchestrator.py` 把 `wait_status_ok()` **串行**在
`wait_app_ready()` 前面，所以应用早就 ready 了，测量却还在等 status check 变 `ok`。
证据是第一轮两个事件相差 2 毫秒（+351.733 s 与 +351.735 s）——
应用不可能刚好在那一刻起来。

**旧数字里 13–17 倍是测量缺陷，不是被测系统的行为。** 已修：
`wait_recovered()` 改为两者并发，以 `app_ready` 为恢复完成判据，
`status_ok` 仅作附加观测。理由不只是测量：status check `ok` 不是服务可用的前提，
玩家能连上才是。

## 恢复段的正确数字

挂死 guest（客户真实故障形态），恢复段合计 `stop + start + app_ready`：

| 停止模式 | 原始值 | 中位数 |
|---|---|---|
| `Force=True`（第一轮用的） | 261.7, 264.6 | **263.1 s** |
| **`SkipOsShutdown=True`（正确参数）** | 21.2, 22.4 | **21.8 s** |

对比第一轮报给客户的 **352.7 s**：正确参数 + 修掉测量缺陷后是 **21.8 s**，
**改善约 16 倍**。

### 端到端

| | 值 |
|---|---|
| 探测段（D1 实测，应用侧探针到请求动作） | 15.5 s |
| 恢复段（本报告，`SkipOsShutdown`） | 21.8 s |
| **端到端合计** | **约 37 s** |
| 客户观测的 AWS auto recovery | 6–7 分钟 |
| **比值** | **约 10–11 倍** |

## 撤销声明

**第一轮的这个结论是错的，现予撤销：**

> ~~「自建恢复路径的收益全部来自检测段（255 s → 15.5 s），恢复段几乎没有改善。
> 因为生产中要 stop 的正是那台已挂死的实例。」~~

错在两处：把 `Force=True` 的超时误认为挂死实例的固有代价；
把自己串行缺陷造成的 89.7 s 当成 OS 启动加应用加载的真实耗时。

**修正后的结论：检测段与恢复段都有大幅改善。**
检测段 255 s → 15.5 s（约 16 倍），恢复段 352.7 s → 21.8 s（约 16 倍），
端到端约 37 秒对客户观测的 6–7 分钟。

这个错误的方向很糟：它会让客户放弃方案里最有价值的那一半。
根因是**只测了一种参数组合、只测了一次，并且没有对自己的测量代码做反向验证**。

## 仍然成立的限定

- **故障类型仍不匹配客户场景。** 本报告注入的是 guest 内 kernel panic，
  只让 instance status check 失败。客户抱怨的是 **system status check** 失败
  （宿主机侧），那一档注入不了，恢复行为仍属 `[待测]`。
  宿主机不可达时 `SkipOsShutdown` 是否同样有效，本次无法验证。
- n=2（panicked）与 n=3（healthy）都偏小。panicked 两组各自极差很小
  （3.8 s / 1.2 s），22 倍的差异远大于组内离散，这个结论是稳的；
  但 healthy 组内的模式差异不成立。
- `SkipOsShutdown=True` 的代价是跳过 OS 关机：可能丢内存内容与在途 I/O、
  跳过关机脚本。客户已声明容忍内存丢失，文件系统用 journaling 即可接受 ——
  但**存盘一致性要由游戏服自己保证**（定期落盘 + 启动时校验），
  不能指望关机流程帮它刷缓存。
