## 第 0 章　一页结论

您提出两个抱怨，实测结果如下：

### 抱怨一：「system status check 报警慢，比应用慢」

**证实，且实际情况比「慢」更严重。**

| 检测通道 | 从故障发生到能看见 | 相对应用侧 |
|---|---|---|
| 应用侧探针判定故障 | **3.5 秒** | 1× |
| 应用侧探针请求恢复动作 | **15.5 秒** | 4× |
| 直接轮询 `DescribeInstanceStatus` API | **255 秒** | **73×** |
| CloudWatch 指标可见（告警能触发的最早时刻） | **319 秒** | **91×** |

三个比「慢」更严重的发现：

1. **短于 60 秒的故障，EC2 侧根本不报。** 不是慢，是漏。
2. **`StatusCheckFailed_System` 对操作系统层故障永远不会失败。** 您要求 AWS 改进的正是这个指标，而它对内核挂死、OOM、文件系统损坏这一整类故障本就不该报。
3. **您当前「靠云厂商自动恢复兜底」的假设，对最常见的一类故障不成立。**

### 抱怨二：「自动恢复时间不可控，成功也要 6-7 分钟」

**证实，并且找到了可以拿回来的那一段。**

| 方案 | 端到端（故障 → 玩家可重连） |
|---|---|
| 现状：等 AWS 自动恢复 | **6–7 分钟**（您的观测） |
| 自建探测 + 编排（用错停止参数 `Force=True`） | 约 4 分 39 秒（改善有限） |
| **自建探测 + 编排（用对停止参数）** | **约 37 秒** |

改善约 **10–11 倍**：检测段 16.5 倍（255 秒 → 15.5 秒），
恢复段 12.1 倍（263.1 秒 → 21.8 秒）。
关键在一个 API 参数：**`SkipOsShutdown=True`**，不是 `Force=True`。

### 这 37 秒不是开箱可得，有三个前提

把它们放在第一页，是因为漏掉任何一条，后面的数字都不成立。

| 前提 | 谁做 | 不做的后果 |
|---|---|---|
| 游戏服健康端点暴露**帧循环推进计数** | 客户应用团队 | 探测退化成 TCP／HTTP 判据，第 4 章两个实验里它们各有 6 秒和 12 轮的假健康 |
| 探测器**部署在区服实例之外**，并配好对照实例 | 客户运维 | 探测器与目标同生共死；或对照失效导致系统永不动作却外观正常 |
| 根卷是 **gp3 / io1 / io2**（不是 gp2） | 客户运维 | 存储故障那一档检测**完全失效**，详见 4.6 |

另有一条**去不掉的**：本方案依赖 EC2 控制面 API，
区域级控制面故障时它与 AWS 自动恢复同时失效。
故障域从「一台实例」缩到「一个区域的控制面」，没有缩到零。

第 11 章列出需要客户自己做的事，第 12 章列出我们做不到的部分。

## 第 1 章　验证方法与可信度说明

### 1.1 环境

| 项 | 值 |
|---|---|
| 被测「区服」 | m7i.large（Nitro）/ Amazon Linux 2023 x86 / 根卷 gp3 20 GB |
| 被测应用 | 桩程序，模拟游戏服帧循环（20 tick/s），暴露 HTTP 健康端点与裸 TCP 端口 |
| 探测器位置 | 同 VPC 同 AZ 另一台实例，跨主机真实网络路径（非 localhost） |
| 对照 sentinel | 同子网同 AZ 的第三台实例 |
| 故障注入 | AWS FIS + SSM，共 9 个用例 |

### 1.2 取证等级约定

报告中每条结论都标注来源，不混用：

- `[实测]` —— 本次在真机上测出，附原始数据路径
- `[文档]` —— AWS 官方文档原文，可引用
- `[待测]` —— 尚未验证，不作为结论
- `[观测值]` —— 来自第三方实测，不是 AWS 承诺值

### 1.3 表格里的统计口径（`n` 是什么）

后文多处表格带 `n` 列，含义统一如下：

| 记号 | 含义 |
|---|---|
| **`n`** | **该组重复测量的次数**（样本数）。`n=3` 表示同一条件下独立跑了 3 次 |
| 最小 / 中位数 / 最大 | 这 `n` 次测量的最小值、中位数、最大值 |
| 组内极差 | 最大值 − 最小值，用来看这组数字自己有多稳 |

我们对 `n` 的使用有一条自我约束：**`n` 小于 3 的组只能作为单点观测报告，
不能用来支撑倍数比较。** 本次有一处刻意破例并说明了理由，
第 3.1 节的 `n=2`，因为两组的组内极差只有 3.8 秒和 1.2 秒，
而两组之间差 240 秒，组间差异远大于组内离散，所以结论是稳的。
相反地，第 3.3 节四组 `n=3` 的范围**互相重叠**，我们就明确写了「无法断言差异」，
没有把中位数的高低当成结论。

第一轮踩过的坑正是 `n=1`：单次测量得出一个 15.3 倍的比值并写进报告，
第二轮复测发现归因错了。所以这一列不是装饰，它是判断「这个数字能不能引用」的依据。

### 1.4 一个方法论声明：本次有两个结论被自己推翻过

第一轮我们曾得出「自建路径的恢复段没有改善」，写进了报告。
第二轮复测发现这个结论是错的，根因是：**只测了一种参数组合、只测了一次、
且没有对自己的测量代码做反向验证。**

我们把错误痕迹完整保留在 `D4-recovery-segments.md`（顶部有撤销声明），
而不是悄悄改数字。这么做的理由是：如果第一轮的结论被采纳，
您会放弃方案里最有价值的一半。**数字的可信度取决于它被质疑过几次，
而不是它看起来多精确。**

## 第 2 章　抱怨一详解：检测为什么慢，慢在哪

### 2.1 同一次故障，四个通道的完整时间线

注入方式：SSM 触发 guest 内 kernel panic 并使其挂住不重启
（`sysctl -w kernel.panic=0` 后 `echo c > /proc/sysrq-trigger`）。

`t_fault = 05:32:04.760`

| 事件 | 绝对时刻 | 相对 t_fault | 出处 |
|---|---|---|---|
| 探测器最后一轮判定健康（tick=3508） | 05:32:04.248 | −0.5 s | 探测器日志 round 19 |
| **探测器判定 `HOST_DOWN`** | 05:32:08.253 | **+3.5 s** | round 20，sentinel 同时正常 |
| 探测器升「软告警」档 | 05:32:14.275 | +9.5 s | 连续 3 次失败 |
| **探测器请求恢复动作** | 05:32:20.296 | **+15.5 s** | 连续 5 次且已持续 12.04 s |
| AWS 声明的 `ImpairedSince` | 05:36:00 | +235.2 s | `InstanceStatus.Details` |
| 指标数据点自身时间戳 | 05:36:00 | +235.2 s | `StatusCheckFailed_Instance=1` |
| **1 秒粒度轮询 API 首次看到 `impaired`** | 05:36:19.802 | **+255.0 s** | `DescribeInstanceStatus` |
| **指标在 CloudWatch 里可见** | 05:37:23.957 | **+319.2 s** | 发布延迟 83.96 s |

### 2.2 三段延迟的构成，以及各自能不能改

| 段 | 秒 | 成因 | 能否改 |
|---|---|---|---|
| AWS 侧检测 | 235.2 | 状态检查每分钟一次，需连续观测到 ARP 无响应 | 只能靠 AWS 改进 |
| 指标发布 | **84.0** | CloudWatch 指标管道固有延迟 | 改不了，但**可以绕过** |
| 告警评估 | 60+ | 评估周期 × 数据点数 | 可减少但有下限 |

**指标发布延迟 84 秒经两次独立测量互相印证**：D1 测到 83.96 秒，
D2 在完全不同的故障类型（存储）上测到 83.1 秒。这是结构性延迟，不是偶发。

**能立刻拿回来的 64 秒**：直接轮询 `DescribeInstanceStatus`（255 秒）
比等指标可见（319 秒）**早 64 秒**。这不需要改任何架构，只需改读取方式，
不要建 CloudWatch 告警去等，而是自己轮询 API。

### 2.3 发现一：短于检查周期的故障根本不上报

第一次注入 panic 时我们踩到一个意外：Amazon Linux 2023 的默认
`kernel.panic = 5`，内核 panic 后 5 秒自动重启，产生的是一次**约 12 秒的自愈重启**。

console output 原文：

```
[  777.799916] sysrq: Trigger a crash
[  777.800284] Kernel panic - not syncing: sysrq triggered crash
[  777.865710] Rebooting in 5 seconds..
```

取证器以 **1 秒粒度**轮完整个 12 秒窗口，结果是：

| 通道 | 观测结果 |
|---|---|
| `DescribeInstanceStatus` 状态转换 | **零次**（全程 `ok/ok/ok`） |
| `StatusCheckFailed_*` 值为 1 的数据点 | **零个** |
| 实例生命周期状态 | **始终 `running`**（reboot 不改变它） |
| 应用侧探针 | **3.8 秒**就判定故障 |

**含义**：您服务器上任何 60 秒以内的故障（进程崩溃后 systemd 重启、
内核 panic 后自动重启、短暂 OOM）在 EC2 监控侧**完全不可见**。
这类事件玩家会感知到（掉线重连），而您的云监控面板上什么都不会显示。

这是「报警慢」之外的一个独立问题，而且更隐蔽。

### 2.4 发现二：`StatusCheckFailed_System` 对 OS 层故障不会失败，因此自动恢复不会介入

内核挂死的整个 5 分钟里：

| 指标 | 值 |
|---|---|
| `instance_status` | `impaired`（`reachability: failed`） |
| **`system_status`** | **始终 `ok`** |
| `attached_ebs_status` | `ok` |

这是**正确的**：宿主机没坏，死的是 guest 内核。

但 AWS 自动恢复的触发条件是 system status check 失败（`[文档]`：
"automatic instance recovery does not operate if only the instance status check fails"）。

**所以下列故障 AWS 自动恢复完全不会介入**：

- 内核挂死 / panic 后不重启
- 进程 OOM 导致系统无响应
- 文件系统损坏导致无法启动
- 驱动 hang
- 错误配置导致网络栈起不来

这类故障下，实例会一直停在 `running` + `impaired` 状态，**永远等不到自动恢复**，
直到有人工介入。您当前「一个区服挂了，云厂商会把它救回来」的假设，
对这一整类故障不成立。

**所以自建探测 + 编排不是「优化」，而是补上一个本来就不存在的兜底。**

### 2.5 发现三：AWS Health 事件通道在当前支持等级下不可用

`DescribeEvents` 返回 `SubscriptionRequiredException`。该 API 需要
Business 或 Enterprise 支持计划。

**含义**：任何依赖「通过 AWS Health 事件提前得知宿主机将退役／已降级」
的方案，在当前支持等级下不成立。如果您希望获得这类提前通知，
需要评估升级支持计划的成本收益。

## 第 3 章　抱怨二详解：恢复慢在哪，以及怎么拿回来

### 3.1 决定性发现：停止参数造成 22 倍差异

对同一台内核挂死的实例，用两种参数调用 `StopInstances`，各重复 2 次：

| 停止参数 | `n`（重复次数） | 最小 | **中位数** | 最大 | 组内极差 |
|---|---|---|---|---|---|
| `Force=True` | 2 | 250.318 | **252.197 秒** | 254.076 | 3.8 秒 |
| **`SkipOsShutdown=True`** | 2 | 10.838 | **11.453 秒** | 12.067 | 1.2 秒 |

原始值：`Force` 组 250.318 与 254.076 秒；`SkipOsShutdown` 组 10.838 与 12.067 秒。

**22 倍差异。** 关于 `n=2` 是否够用：按第 1.3 节的自我约束，`n<3` 一般不支撑倍数比较，
这里刻意破例并说明理由：两组的**组内极差只有 3.8 秒和 1.2 秒**，
而两组**之间**差约 240 秒，组间差异比组内离散大两个数量级，所以这个结论是稳的。
另一个佐证是 `Force` 组的 252.2 秒**复现了第一轮独立测得的 257.2 秒（差 2%）**，
两次不同时间、不同实例的测量互相印证。

### 3.2 机制：`Force=True` 不是您以为的意思

`StopInstances` API 参考原文（`[文档]`）：

> **Force** — Forces the instance to stop. The instance **will first attempt a
> graceful shutdown**, which includes flushing file system caches and metadata.
> **If the graceful shutdown fails to complete within the timeout period**,
> the instance shuts down forcibly without flushing the file system caches and metadata.

也就是说 `Force=True` 是「**先试优雅关机，超时后才硬下电**」。
对一个内核已 panic、永远完不成关机流程的实例，它必须把那个超时**整个走完**
—— 实测约 250–254 秒，数值稳定得像一个固定超时常量。

真正绕过 OS 关机流程的是另一个参数：

> **SkipOsShutdown** — Specifies whether to bypass the graceful OS shutdown
> process when the instance is stopped.

**注意**：早期版本的 SDK 文档把 `Force` 描述成「不给实例刷缓存的机会」，
与现行 API 参考不一致。如果您的运维脚本是照旧文档写的，
很可能正在用 `Force` 而不知道它会等超时。这一条值得您回去核查现有脚本。

### 3.3 三档 guest 状态：差异在「应用不响应 SIGTERM」时暴露

停止参数的影响取决于 guest 处于什么状态。三档都测了：

| guest 状态 | 应用响应 `SIGTERM`？ | 普通 stop | `SkipOsShutdown` | 差异 |
|---|---|---|---|---|
| 健康 | 响应，正常退出 | 16.4 s | 12.0 s | **不可断言**（n=3 区间重叠） |
| **应用冻死、OS 正常** | **不响应** | **103.4 s** | **5.7 s** | **18.2 倍** |
| 内核已死 | 内核都没了 | 252.2 s | 11.5 s | 22 倍 |

中间那一档最重要，因为**它才是恢复动作最常面对的状态** ——
`APP_STUCK` / `APP_DEAD` 时操作系统完全正常，只是游戏进程冻住了。

**机制**：进程不响应 `SIGTERM` 时，systemd 会等满 `TimeoutStopSec`
（Amazon Linux 2023 默认 **90 秒**）才发 SIGKILL。实测普通 stop 的
99.3–103.4 秒里，约 90 秒就是这个超时。`SkipOsShutdown=True`
直接绕过整个 OS 关机流程，所以不受它影响。

**这一档是补测的，补测前我们的依据是错的。** 原先拿健康实例那组
（四种模式无法区分）来论证参数选择，而健康实例的应用**会**响应 `SIGTERM`，
从来碰不到那个超时 —— 用一个条件下的结论去支撑另一个条件下的决策。
详见 `D11` 报告。

**所以准确的说法是**：差异在「应用不响应 `SIGTERM`」的实例上暴露，
既包括内核已死的，也包括 OS 正常但进程冻住的。
唯一看不出差异的是健康实例 —— 而**恢复动作从不作用于健康实例**。

> 这里有一个演练陷阱：如果您拿一台健康实例做演练来「验证恢复流程」，
> 两种参数看起来一样快，于是这个 18–22 倍的缺陷**在演练中完全不暴露**，
> 只在真实故障时暴露。演练必须用真正卡住的实例。

#### 健康实例那一档的明细（为什么它看不出差异）

| 模式 | `n`（重复次数） | 最小 | 中位数 | 最大 |
|---|---|---|---|---|
| 不传参数 | 3 | 14.171 | 16.357 | 18.207 |
| `Force=True` | 3 | 16.308 | 18.621 | 20.548 |
| `SkipOsShutdown=True` | 3 | 8.688 | 11.996 | 17.315 |
| 两者都传 | 3 | 5.467 | 10.969 | 17.780 |

四组范围**全部重叠**，n=3 不足以断言差异。诚实的说法是：
**健康实例上四种模式无法区分，都在 5–21 秒带内。**

原因是健康实例的应用**响应 `SIGTERM` 并正常退出**，优雅关机几秒就走完了，
所以从来碰不到 systemd 的 90 秒超时 —— 那个超时只在进程**不肯退出**时才计满。
**参数选错的代价，只在真出故障时才付。**

### 3.4 恢复段的完整构成

挂死实例，用 `SkipOsShutdown=True`：

| 分段 | 中位数 | 说明 |
|---|---|---|
| `StopInstances` API 返回 | 0.4 秒 | |
| running → stopping | 2.1 秒 | |
| **stopping → stopped** | **11.5 秒** | 关键段 |
| stopped → running | 3.3 秒 | 换到新宿主机 |
| **running → 应用真正可服务** | **7.0 秒** | n=12，范围 6.0–7.1，非常稳定 |
| **恢复段合计** | **21.8 秒** | |

### 3.5 一个必须纠正的运维习惯：不要用 status check 判断恢复完成

| 判据 | 从 `running` 起的耗时 |
|---|---|
| **应用真正可服务**（健康端点的推进计数在动） | **7.0 秒** |
| `status check` 变 `ok` | **88–122 秒**，且方差达 37% |

**差一个数量级以上。** 如果您的恢复流程等 status check 变 `ok` 才放玩家进来，
每次恢复都白等一分半以上，而且这个等待时长本身不稳定。

（补充说明：我们第一轮的编排器就犯了这个错 —— 把等 status check 串在
等应用之前，导致把「应用就绪」这一段测成了 89.7 秒和 121.8 秒，虚高 13–17 倍。
改为并发采集后才拿到 7.0 秒这个真实值。这个错误值得您在自己的运维脚本里也查一遍。）

### 3.6 端到端

| 段 | 秒 |
|---|---|
| 检测（应用侧探针到请求动作） | **15.5** |
| 恢复（`SkipOsShutdown` 路径） | **21.8** |
| **合计** | **约 37 秒** |

对比您观测的 AWS 自动恢复 6–7 分钟：**约 10–11 倍**。

### 3.7 代价与前提

`SkipOsShutdown=True` 跳过 OS 关机流程，可能丢失内存内容、在途 I/O、
以及关机脚本。您已明确「能容忍内存丢失」，文件系统用 journaling 可接受，
但有一个**必须由游戏服自己保证**的前提：

> **检查点一致性。** 周期性检查点 + 启动时校验存档完整性。
> 不能指望关机流程帮你刷文件系统缓存 —— 这条路上没有关机流程。

### 3.8 能不能干脆用告警动作代劳？不能，而且原因正是本章的核心

看到这里很自然会问：既然 CloudWatch 告警自带 `stop` 动作，
为什么还要自建编排器？直接挂个 `arn:aws:automate:<区域>:ec2:stop` 不就行了？

**不行，原因是告警动作无法传参数。**

告警动作是一个固定形态的 ARN，它不携带任何参数，
因此**没有任何办法让它带上 `SkipOsShutdown=True`**。
而本章的全部结论就建立在这个参数上：

| 停止方式 | 挂死实例上的耗时 | 能否用告警动作实现 |
|---|---|---|
| `SkipOsShutdown=True` | **11.5 s** | **不能** —— ARN 传不了参数 |
| 默认 / `Force=True` | **252 s** | 能，但这正是慢的那一档 |

也就是说：**告警动作的 `stop` 会退化到 252 秒那一档，
而且恰恰是在最需要它快的那类实例上退化** —— 关不掉的挂死实例。
在健康实例上它看起来很快（第 3.3 节：四种模式无法区分），
于是这个缺陷在演练中不会暴露，只在真实故障时暴露 ——
而真实故障里它要么多花约 90 秒的 systemd 超时（应用冻死），
要么多花约 252 秒（内核已死）。

这是自建编排器的**主要理由**，比「检测更快」更根本：
不是我们想自己写，而是托管动作表达不出需要的语义。

**但告警动作作为演练手段很有价值**（实测确认三种动作都真的会执行）：

| 用途 | 可行性 |
|---|---|
| 演练「stop 之后系统能不能自己回来」 | **可行**，一条 `set-alarm-state` 即可，不需要 FIS |
| 演练 reboot 路径 | **可行**，但必须用 uptime 判定，实例状态全程不变 |
| 演练 terminate 后的重建流程 | **可行**，实测 7 秒完成 |
| 替代编排器做生产恢复 | **不可行**，见上 |

> 演练前务必 `disable-alarm-actions` 或使用一次性实例：
> 这三种动作会**真的**停掉、重启或销毁实例。详见第 6.4 节。

## 第 4 章　探测判据怎么选：三个判决性实验

您问「用 TCP 还是 ping」。**先给结论，后面三个实验是它的证据。**

### 4.0 推荐的探测判据（一句话版）

> **触发器只有一个：游戏服健康端点返回的「帧循环推进计数」是否在推进。
> TCP 与 ICMP 都不做触发器，只做分类器，用来决定动作到哪一级。
> 存储故障另走旁路信号，因为推进计数看不见它。**

展开成四条：

| # | 角色 | 用什么 | 判据 | 为什么不是别的 |
|---|---|---|---|---|
| 1 | **触发器**（决定要不要动作） | 健康端点 `tick` 计数 | **计数在推进** | TCP 可连、HTTP 200 都会在进程死透时继续为真，见 4.1、4.2 节 |
| 2 | 分类器（决定动作到哪一级） | TCP connect 游戏端口 | 端口是否可连 | 区分「进程没了」与「整台不可达」 |
| 3 | 分类器 | ICMP ping | 内核网络栈是否活着 | 区分「重启进程就够」与「必须换宿主机」，见 4.3 节 |
| 4 | 分类器（抑制误动作） | 同 AZ 同子网的对照实例 | 对照是否也不可达 | 区分「被测方坏了」与「我这边坏了」 |
| 5 | **旁路触发器**（补盲区） | `DescribeVolumeStatus` 的 `io-performance` | 卷 I/O **不正常**（含性能劣化，不只停滞） | 推进计数对存储故障完全是盲的，见第 5 章。**有卷型硬前提，见 4.6** |
| 6 | 旁路触发器（补盲区） | 健康端点「上次成功存档的时间戳」 | 是否超过落盘周期的若干倍 | 抓「还在跑但注定丢档」这个最坏状态，见 5.4 节 |

**三条不该用的判据**，以及不该用的原因：

| 判据 | 为什么不行 |
|---|---|
| 只看 TCP 端口可连 | 内核 backlog 会代替死进程完成握手，实测假阴性持续 6 秒以上（4.1） |
| 只看 HTTP 200 | 健康端点由独立线程提供时，主循环冻死它照样回 200，实测连续 12 轮假健康（4.2） |
| 只看 ICMP 可达 | 内核活着而应用死了时它照样通，它是分类器不是存活判据（4.3） |

**一句话记法**：判据要看**响应体的内容在变**，不是看端口通、也不是看响应码对。

### 4.0.1 「推进计数」到底是什么，怎么实现

这一节讲清原理，因为它是整套方案的基石，而且**必须由客户的应用团队实现**，
不是我们能代做的部分。

#### 它是什么

游戏服都有一个主循环：每一帧（或每个逻辑周期）处理玩家输入、推进世界状态、
结算战斗、准备下一帧。**「推进计数」就是这个主循环转了多少圈的累加计数。**

行业里管这一圈叫 **tick**，所以下面用 `tick` 指代它。
它不是新概念，也不需要新逻辑——绝大多数游戏服内部本来就有这个数，
只是没往外暴露过。

#### 游戏服要做的事：两行代码

在主循环里加一个自增，并让健康端点把它读出来。

```python
tick = 0

while running:
    process_input()        # 你原本的逻辑
    update_world()
    resolve_combat()
    tick += 1              # ← 加这一行
    sleep_until_next_frame()
```

健康端点返回一个 JSON，把它带上：

```
GET /health
{"tick": 481923, "loop_lag_ms": 3.2, "players": 812}
```

**关键在于这个数必须由主循环自己自增。** 如果它由别的定时器或独立线程维护，
判据就失效了——那个线程活着不代表游戏在跑。这一点是 4.2 节实验的核心。

#### 探测器怎么判

探测器每轮取一次 `tick`，和上一轮比：

| 本轮取到的 | 判定 | 说明 |
|---|---|---|
| 数值**变了** | 推进中 | 主循环在转，游戏活着 |
| 数值**没变**，且未超阈值 | 暂不判故障 | 可能只是刚好卡在两次采样之间 |
| 数值**没变**，且已持续超过阈值 | **判为卡死** | 主循环停了 |
| 端点取不到 `tick` 字段 | **测不出来** | 不当作正常，也不当作故障 |

实现上有个细节：探测器记的是**「上次看到数值发生变化」的时刻**，
而不是「连续几轮没变」的次数。这样阈值就是一个物理时间量（秒），
和轮询间隔解耦——把间隔从 1 秒改成 2 秒，判据行为不变。

首轮无从比较，按「推进」处理，由后续轮次纠正。

#### 为什么必须是「计数在变」，不能是别的

这里有三个层次，一层比一层深：

| 判据 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 端口可连 | 内核网络栈在工作 | 进程是否存在（内核会代替死进程握手，4.1） |
| HTTP 200 | 有个线程在响应请求 | 主循环是否在跑（响应线程独立存活，4.2） |
| **`tick` 在变** | **主循环真的在推进世界状态** | 存储是否健康（这是它的盲区，第 5 章） |

三者的区别可以这样理解：前两个证明的是「这台机器上还有东西在应答」，
只有第三个证明「玩家的游戏还在继续」。

而这正是要判断的东西——玩家关心的不是端口通不通，是他的角色还能不能动。

#### 阈值怎么定

阈值（默认 6 秒）必须**大于该区服正常运行时最长的一次主循环停顿**。
主循环会因为垃圾回收、检查点落盘、大批量结算而短暂卡顿，
这些都是正常的，不该触发动作。

正确做法是跑一段真实业务，统计 `tick` 间隔的分布，取观测最大值的若干倍，
**并记录「这个阈值在历史数据上会误触发多少次」**。不要拍一个看起来安全的整数。

#### 三种会让判据失效的错误实现

| 错误实现 | 为什么失效 |
|---|---|
| 用**独立线程**维护计数 | 主循环冻死时它照常自增，退化成一个花哨的 HTTP 200 |
| 返回**时间戳**而不是计数 | 时间戳自己会走，与主循环是否在跑无关 |
| 计数**会重置或回绕** | 探测器判的是「变了没」，重置也算变，会掩盖一次重启 |

第一种最危险，因为它看起来完全正确、日常运行毫无异常，
只在真出故障时静默失效。

#### 它便宜到可以忽略成本

一个整数自增，加上健康端点读一次共享变量。
没有 I/O，没有锁竞争（读旧值也无妨——探测器要的是「变没变」，不是精确值）。

也正因为这样，**这条判据的成本远低于它的价值**：
它是唯一能区分「服务器还活着」和「玩家还在玩」的信号。

#### 参考实现：`design/scripts/health_endpoint_reference.py`

我们提供了一份**可直接抄的完整实现**，并在真机上跑通验证过。
用 Python 写是为了能立即运行验证，但每条约束都与语言无关。

核心部分：

```python
class GameState:
    def __init__(self):
        self.tick = 0                                # 只由主循环自增
        self.last_checkpoint_success_timestamp = 0.0  # 只在成功时更新

STATE = GameState()

# 健康端点：独立线程，只读内存，绝不碰磁盘
class HealthHandler(BaseHTTPRequestHandler):
    def do_GET(self):
        body = json.dumps({
            "tick": STATE.tick,
            "last_checkpoint_success_timestamp":
                round(STATE.last_checkpoint_success_timestamp, 3),
            "players": STATE.players,
            "loop_lag_ms": round(STATE.loop_lag_ms, 3),
        }).encode()
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.send_header("Cache-Control", "no-store")   # 见下方约束
        self.end_headers()
        self.wfile.write(body)

# 主循环
while True:
    t0 = time.monotonic()

    process_input(); update_world(); resolve_combat()   # 你原本的逻辑

    STATE.tick += 1                                     # 只有这里自增
    STATE.loop_lag_ms = (time.monotonic() - t0) * 1000.0

    if t0 >= next_checkpoint:
        next_checkpoint = t0 + checkpoint_interval_s
        if do_checkpoint(path):                         # 内部真的 fsync
            STATE.last_checkpoint_success_timestamp = time.time()
            # 失败时刻意不更新 —— 让滞后量自己涨上去

    time.sleep(max(0.0, period - (time.monotonic() - t0)))
```

#### 六条约束，每条对应一个真实故障场景

| # | 约束 | 违反的后果 |
|---|---|---|
| 1 | `tick` 只能由**主循环自己**自增 | 独立线程维护时，主循环冻死它照常涨，判据失效 |
| 2 | 健康端点跑在**独立线程**，只读不写 | 端点阻塞主循环，或反过来被主循环拖死 |
| 3 | **健康端点绝不做磁盘 I/O** | 见下方说明，这条最隐蔽 |
| 4 | 检查点必须真的 `fsync` | 只进页缓存时，「成功」在存储故障期是假的 |
| 5 | 检查点**失败时绝不更新时间戳** | 把「一直在丢档」伪装成健康 |
| 6 | `tick` 单调递增，不重置不回绕 | 重置也算「变了」，掩盖一次进程重启 |

**约束 3 值得单独解释**，因为它反直觉：健康端点里加一句「顺便检查存档文件能不能读」
看起来是增强，实际会制造一个严重的误分类。

存储停滞时，若端点要读盘才能应答，它会**跟着一起挂住** →
外部探测器取不到响应，判成「应用死了」→ 动作阶梯执行**重启进程** →
重启后的进程一去读盘就卡在不可中断等待里，**起不来**。
一次可恢复的存储故障，被处置成了一台起不来的机器。

端点只读内存，存储停滞时它才能照常回答
「我还在应答，但检查点在超时」，探测器才能分类正确、走对动作。

另外那个 `Cache-Control: no-store` 不是摆设：中间层若缓存了健康响应，
探测器会一直看到同一个 `tick`，把健康的服务判成卡死。

#### 关于并发读取：不要加锁

健康端点可能读到「上一轮的旧 `tick`」，这**完全没问题**——
判据是跨轮次的变化，不是某一瞬间的精确值。

| 语言 | 做法 |
|---|---|
| C++ | `std::atomic<uint64_t>`，`memory_order_relaxed` 足够 |
| Go | `atomic.AddUint64` / `atomic.LoadUint64` |
| C# | `Interlocked.Increment`，或 `volatile long` |

**不要为此引入互斥锁。** 主循环是热路径，锁竞争代价远大于收益；
而且健康端点持锁期间一旦被调度出去，反而会拖慢主循环——
为了监控而伤害被监控对象。

#### 这份实现的验证结果

| 断言 | 结果 |
|---|---|
| 30 Hz 下 `tick` 一秒增长 31 | PASS |
| 探测器识别该端点并全程判健康 | PASS，6 轮 |
| 检查点写盘且无临时文件残留 | PASS |
| 检查点失败期端点**仍能应答** | PASS |
| 检查点失败期 `tick` **仍在推进** | PASS，240 → 330 |
| 检查点失败期时间戳**被冻结** | PASS，滞后量涨到 10.0 秒 |

最后三条一起验证的是那个最坏状态：**游戏还在跑、玩家还在玩，但进度已经丢了。**
这个状态只有把 `tick` 和检查点时间戳分开暴露才看得见。

下面三个实验分别证明为什么端口、响应码、ICMP 都不够。

### 4.1 实验一：TCP connect 不能当存活判据

对游戏服进程发 `SIGSTOP`（进程进入 `State: T (stopped)`，完全冻死）：

| 轮次（1 秒间隔） | TCP 7777 | 判定 |
|---|---|---|
| 1 – 6 | **`open`** | 进程完全冻死，TCP 仍握手成功 |
| 7 – 18 | timeout | listen backlog 填满后才开始超时 |

**机制**：内核用 listen backlog 代替一个死进程完成了三次握手。
**假阴性窗口的长度由 backlog 深度和探测频率决定，与进程健康无关。**

在您的生产环境里，backlog 通常配得比这个桩程序大得多，
所以这个假阴性窗口只会**更长**。

### 4.2 实验二：HTTP 200 也不够

只冻主循环（HTTP 与 TCP 服务线程继续工作）：

| 轮次 | HTTP | TCP | 推进计数 | 判定 |
|---|---|---|---|---|
| 1 – 5 | 200 | open | 204→284 递增 | 健康 |
| 6 – 10 | 200 | open | **300 冻住** | 尚在容忍窗口内 |
| 11 – 22 | **200** | **open** | **300 冻住** | **故障** |

**连续 12 轮 HTTP 返回 200 且 TCP 可连，而服务实际已停止推进。**
纯 TCP 判据和纯 HTTP-200 判据在这 12 轮里全部判健康。

**结论：判据必须是响应体内容在推进，不是响应码。**

### 4.3 实验三：ICMP 的作用是分类，不是检测

| ICMP | 游戏端口 | 判定 | 该做什么 |
|---|---|---|---|
| 通 | 不通 | 进程没了 | 重启服务，不必换宿主机 |
| 不通 | 不通 | 宿主机／实例侧 | 换宿主机 |

ICMP 单独用不能检测存活（内核活着但应用死了时它照样通），
但它是区分「重启进程就够」和「必须换宿主机」的唯一廉价手段。

### 4.4 完整判据真值表（4.0 给角色，这里给「每种组合分别做什么」）

4.0 说的是每个信号扮演什么角色，下表是把它们组合起来后的完整对照 ——
每一行对应一种可区分的故障形态和一级动作：

| 推进计数 | TCP | ICMP | 对照 | 卷 I/O | 检查点滞后 | 判定 | 动作 |
|---|---|---|---|---|---|---|---|
| — | — | — | — | **不正常** | — | 存储故障 | **换宿主机，绝不重启进程** |
| 推进 | — | — | — | 正常 | **超龄** | 注定丢档 | **告警，刻意不动作** |
| 推进 | — | — | — | 正常 | 正常 | 健康 | 无 |
| 推进但响应慢 | — | — | — | 正常 | 正常 | 慢 | 仅告警 |
| **冻住** | **通** | — | — | 正常 | — | 进程卡死 | 重启服务 → 换宿主机 |
| 端点不通 | 通 | — | — | — | — | 进程卡死 | 重启服务 → 换宿主机 |
| — | 不通 | 通 | — | — | — | 进程没了 | 重启服务 → 换宿主机 |
| — | 不通 | 不通 | **正常** | — | — | 宿主机故障 | 直接换宿主机 |
| — | 不通 | 不通 | **也不通** | — | — | **探测侧问题** | **永不动作** |
| — | 不通 | 测不出 | 测不出 | — | — | **无法判断** | **永不动作** |

表里有三行的动作是「不做常规处置」，每一行的理由都不同，值得单独记住：

| 行 | 为什么这么处置 |
|---|---|
| 存储故障 → **绝不重启进程** | 卷 I/O 已停滞，重启后的进程一去读盘就挂在不可中断状态起不来，比不动更糟 |
| 注定丢档 → **刻意不动作** | 未落盘的进度是此刻最危险的东西，而重启和 stop/start **都会销毁它**。该由运营决定是继续玩还是主动踢下线 |
| 探测侧问题 / 无法判断 → **永不动作** | 一个区服 = 一整批在线玩家，宁可漏动作也不能误动作 |

**行的顺序就是判定优先级**：存储故障排在最前面，因为在那种情况下
推进计数仍然是「正常」的（第 5 章实测 427 轮全绿），
若先看应用侧判据，存储这一支永远进不来。

### 4.5 阈值建议

| 参数 | 建议值 | 依据 |
|---|---|---|
| 探测间隔 | 1–2 秒 | 决定检测下限 |
| 软告警阈值 | 连续 3 次 | 只告警不动作 |
| 硬动作阈值 | 连续 5 次 **且** 已持续 ≥8 秒 | 两条是「与」关系 |
| 推进停滞判定 | > 检查点与 GC 停顿的 P99.9 | **必须实测该区服自己的分布，不要拍整数** |
| 动作冷却期 | 600 秒 | 防止一次故障放大成一串重启 |

硬阈值同时要求「次数」和「时长」的理由：只用次数时，
一串 50 毫秒内连续失败的探针就能立刻触发一次区服重启。

实测该机制有效：故障期间探测器发出 1 次动作请求，随后 12 次全部被冷却期抑制。

### 4.6 存储判据有一个卷型硬前提

上表第 5 行那条旁路判据**不是所有卷都能用**：
`io-performance` 只有 `io1` / `io2` / `gp3` 卷才有，**`gp2` 卷用不了**。

老实例的根卷默认往往是 gp2，在这些机器上这条判据一点作用都没有。
**上线前必须逐台核实卷型**，两种处置方式与我们自己在这里踩过的一个误动作缺陷，
都写在 5.6 节。

## 第 5 章　一个反直觉的盲区：存储故障

### 5.1 现象：根卷 I/O 全停 3 分钟，应用毫无反应

用 FIS 暂停根卷 I/O 3 分钟：

| 观测项 | 结果 |
|---|---|
| 探测器总轮数 | 427 |
| **判定为故障的轮数** | **0** |
| 推进计数 | 25408 → 33910，**无回退** |
| ICMP | 全程通 |
| `instance_status` / `system_status` | 全程 `ok` |

**根卷 I/O 全停 3 分钟，玩家侧毫无感知。**

原因：游戏主循环全在内存里跑，页缓存够用，不需要新的磁盘读，
所以帧循环照常推进。只有真正要碰盘的东西（检查点、写日志）挂住了。

### 5.2 这带出两个后果

**后果一：推进计数判据对存储故障是盲的。**
这是整套方案里**唯一一个 EC2 侧信号优于应用侧探针**的场景
（其余场景都是应用侧 3.5 秒对 EC2 侧 255 秒）。必须靠旁路信号补上。

**后果二：存在比「服务不可用」更糟的状态。**
游戏还在跑、玩家还在玩、帧率正常，但**所有检查点都失败**，
这是一局注定丢档的游戏。对玩家而言，这比直接掉线更难接受。

### 5.3 存储故障的判据选择（按实测有效性排序）

| 优先级 | 判据 | 实测延迟 |
|---|---|---|
| 1 | `DescribeVolumeStatus` 的 `io-performance` 不为 `normal`（四档：`degraded` / `severely-degraded` / `stalled`） | **+112.7 s** ／ **+144.6 s**（两次） |
| 2 | `DescribeInstanceStatus` 的 `AttachedEbsStatus` | **+155.7 s** |
| 3 | `StatusCheckFailed_AttachedEBS` 告警 | **+218.9 s** |
| 不可用 | **`VolumeStalledIOCheck`** | **永不触发**，见 6.1（第 6 章）|
| 不可用 | `VolumeReadOps`/`WriteOps` 高于阈值 | **永不触发**，注入期归零，方向相反 |

又一次印证「直接轮询 API 快于指标通道」：本例快 **63 秒**。

> **优先级 1 这条判据有卷型硬前提**：`io-performance` 仅 `io1` / `io2` / `gp3` 支持，
> **`gp2` 卷返回 `not-applicable`，该判据完全失效**。
> 上线前必须逐台核实根卷卷型，详见 4.6 节。

### 5.4 「注定丢档」这个状态的正确处置：不要自动处置

我们实现了对它的检测（游戏服暴露「上次成功存档的时间戳」，
探测器据此判定），但**刻意让这一档不触发任何自动动作**。

理由：帧循环还在推进时，**未落盘的进度是此刻最危险的东西，
而每一种自动恢复动作都会销毁它** —— 重启进程丢内存，stop/start 也丢内存。

所以唯一正确的自动行为是「告警 + 不动作」，由运营去权衡：

- 让玩家继续玩，赌存储很快恢复，但可能丢更多进度
- 主动踢下线，保住已落盘的进度

这是一个**业务决策，不是技术决策**，不该由自动化替您做。

---

### 5.5 这条判据具体怎么执行

5.3 选出的判据走 **AWS 控制面 API**，完全不碰目标主机：
独立后台线程轮询 `DescribeVolumeStatus`，与应用侧四条探针并行且互不阻塞
（API 调用可能超时重试，塞进 1 秒主循环会拖垮秒级检测节奏）。

必须绕开主机的第二个理由：进程一旦碰到停滞的卷，就自己卡在不可中断的 I/O 等待里，
连「我有问题」都报不出来。

`io-performance` 这一项有**四档**状态，不只「停滞」一档：

| `io-performance` | 含义 | 判定 |
|---|---|---|
| `normal` | 性能正常 | 健康 |
| `degraded` | 性能低于预期 | **异常**（这是「延迟劣化」档） |
| `severely-degraded` | 性能远低于预期 | **异常** |
| `stalled` | 性能严重受损 | **异常** |
| `not-applicable` | **该卷型不支持此检查** | **测不出来**，既非正常也非故障 |

### 5.6 一个必须先确认的硬前提：卷型

**`io-performance` 检查仅 `io1` / `io2` / `gp3` 卷支持。`gp2` 卷没有这项检查。**

实测确认：

| 卷型 | 返回值 |
|---|---|
| gp3 | `normal` |
| **gp2** | **`not-applicable`** |

**这个前提必须在上线前逐台核实。** 老实例的根卷默认往往是 gp2，
在这些机器上这条存储旁路**完全不生效**。

处置有两条路，二选一：

1. **把根卷改成 gp3**（可在线修改卷类型，不需停机），获得这条检测通道
2. **保持 gp2，但明确承认存储故障只能靠应用侧的检查点滞后判据**发现，
   并把这一点写进运维手册，而不是以为有旁路在保护

程序的处理方式是：启动时预检卷型，配置的卷全不支持时**拒绝启用该旁路并说明原因**，
不允许带着一条永久失效的检测通道静默运行。

> 这里我们自己犯过一个会造成误动作的错误，已修复：
> 原代码判「状态不等于 `normal` 即为故障」，于是 `not-applicable` 被当成停滞，
> **每个 gp2 卷都会被无条件触发一次 stop/start**，而日志上显示「检测到存储停滞」，
> 看起来完全正常。已改为显式列举状态并把「测不出来」独立表达，
> 用真实 gp2 与 gp3 卷做了五条断言的反向验证。详见 `D10` 报告。

### 5.7 存储「延迟」能带外判断到什么程度

带外能判断的和不能判断的，要分清：

| 想知道的 | 带外能否判断 | 说明 |
|---|---|---|
| 卷是否不正常 | **能** | 四档状态，含性能劣化 |
| **具体有多慢** | **不能** | 延迟是**写入方感受到的东西**；带外只有聚合后的分钟级判定 |
| 业务受多大影响 | **不能** | 同上 |

因此分工是：

- **快路径在带内**：游戏服自报检查点滞后。存储变慢的直接后果就是检查点滞后增大，
  **已被 `CHECKPOINT_LAGGING` 判据覆盖，不需要另外去带外测延迟**
- **带外通道负责归因与兜底**：确认「是卷的问题不是应用的问题」，
  以及在应用侧字段缺失时提供一个虽慢但存在的信号

一句话：**带外看得见「卷不正常」，看不清「有多慢」；
「有多慢」的业务后果由带内的检查点滞后表达。**

### 5.8 两条实现时容易踩的坑

`VolumeStalledIOCheck` 是 AWS 文档明文推荐用来检测 I/O 停滞的指标，
本环境实测**一个数据点都没有**。照文档配这个告警，得到的是一个永远停在
`INSUFFICIENT_DATA` 的告警。

`VolumeReadOps` / `WriteOps` 在 I/O 停滞时是**归零**，按「超过阈值告警」配方向正好搞反。

## 第 6 章　五个会造成监控盲区的陷阱（全部实测）

这一章是本次验证副产品里最值得您复查现有监控的部分。

### 6.1 `VolumeStalledIOCheck` 零数据点 —— 与 AWS 文档矛盾

AWS 文档明确推荐（`[文档]`）：
「The CloudWatch metric for `VolumeStalledIOCheck` will be 1 if volume I/O
is paused for over 60 seconds」。

本账号本区实测（`[实测]`）：

| 检查 | 结果 |
|---|---|
| `list-metrics` 能否列出该指标 | **能** |
| `get-metric-data` 数据点个数 | **0**（`StatusCode: Complete`，时间戳数组为空） |
| 同期卷是否真的停滞 | **是**，卷状态明确 `io-performance: stalled`，事件写着 `I/O throughput (0%) is severely impacted` |

**后果**：任何建在这个指标上的 CloudWatch 告警会**永久停在 `INSUFFICIENT_DATA`，
永不触发**。若再配 `--treat-missing-data notBreaching`，它会一直显示「正常」——
一个看起来健康的监控盲区。

**行动项**：请检查您现有告警里是否有建在这个指标上的。
更一般地：**「指标名字列得出」不等于「指标在发布数据」，
建告警前必须 `get-metric-data` 实际取一次并数数据点个数。**

### 6.2 对照目标默认是不可达的

我们按计划复用账号里现有实例做探测对照，实测发现**三台候选从探测器主机全部不可达**：
一台的安全组入站规则一条都没有，另一台只放行别的网段。

**如果不做这次阳性对照就上线**，对照会永远失败，探测器会把**每一次真实故障**
都判成「探测侧问题」而抑制动作 —— **整套自愈静默失效，而监控面板上一切正常。**

**行动项**：任何「对照组」「基线」「哨兵」机制上线前，必须先证明它在正常状态下是活的。
我们把这一条做成了探测器的**启动硬条件**：对照不可达就拒绝启动并打印修复提示，
不允许静默降级。

### 6.3 `describe_instance_status` 默认只返回异常实例

不传 `IncludeAllInstances=True` 时，健康实例返回**空列表** ——
而空列表与「实例不见了」无法区分。

**行动项**：检查现有巡检脚本是否漏了这个参数。

### 6.4 `Action completed successfully` 只描述投递，不描述执行

我们尝试用 `set-alarm-state` 强制触发挂了自动恢复动作的告警，
告警历史 1.6 秒就报 `Action completed successfully`。

**但实例从未被恢复。** 四条独立证据：

| 证据 | 观测 |
|---|---|
| CloudTrail | 窗口内 `RecoverInstances` **0 条**、`RebootInstances` **0 条** |
| 1 秒粒度轮询 8 分钟 | 状态转换 **0 次**、生命周期转换 **0 次** |
| 应用推进计数 | 8825 → 19721 单调递增，**无回退**（进程从未重启） |
| `DescribeInstanceStatus.Events` | `null` |

**机制**：那句成功表示 CloudWatch 成功把动作**投递**给了 EC2，
不表示 EC2 **执行**了迁移。EC2 的恢复动作会校验实例是否真的受损，
系统状态检查真实通过时它是空操作。

**限定范围（已由后续实测收窄）**：上面那个「空操作」的结论**只对 `recover` 成立**。
我们后来把另外三种告警动作也测了，结果相反：

| 告警动作 | 是否真的执行 | 证据 | 首次可见 |
|---|---|---|---|
| `recover` | **否，空操作** | CloudTrail 零记录、零状态转换 | 未发生 |
| **`reboot`** | **是，真的重启了** | uptime 由 377 s **回退**到 226 s | 约 t+26 s |
| **`stop`** | **是** | 状态转 `stopping` | **t+1 s**，t+23 s 到 `stopped` |
| **`terminate`** | **是** | 状态转 `shutting-down` | **t+1 s**，t+7 s 到 `terminated` |

CloudTrail 显示 `RebootInstances` / `StopInstances` 的发起方是
`events.amazonaws.com`，证明确实由告警动作发起，不是我们手工调的 API。

**所以 AWS 文档那条「测试前先 `disable-alarm-actions` 以免意外重启实例」的警告
完全成立，而且比警告说的更严重 —— 它同样适用于 `stop` 和 `terminate`。**

> **一条运维安全警告**：如果您的告警挂的是 `stop` 或 `terminate` 动作，
> 用 `set-alarm-state` 去「测一下告警通不通」会**真的停掉或销毁生产实例**，
> 而且 `terminate` 在实测中只用了 **7 秒**。
> 测试前务必 `disable-alarm-actions`，或在一次性实例上测。

**这一条仍然成立且证据更强了**：`Action completed successfully`
**只描述投递，不描述执行**。同一句话，在三种动作上对应真实执行，
在 `recover` 上什么都没发生 —— **同一条消息文本，两种截然不同的事实。**

**行动项**：
1. 如果您曾用 `set-alarm-state` 验证过**自动恢复（recover）**链路并认为「验证通过」，
   那次验证是无效的
2. 反过来，`reboot` / `stop` / `terminate` 三条路径**可以**用一条 API 调用低成本反复演练，
   不需要 FIS。这是个便宜的演练手段，见第 3.8 节

### 6.5 安全组规则 ID 在 revoke / re-authorize 后会变

收回再加回不是幂等操作，AWS 生成全新的规则 ID。
按旧 ID 写的清理／回滚脚本会静默失败。

## 第 7 章　AWS 对这个场景有专门指引，层次比本方案更高

这一章是内部评审时补做的调研结果，**它会影响您对本方案定位的判断，请务必读。**

### 7.1 GAMEREL03：标题就是您的问题

AWS Well-Architected 有一份 **Games Industry Lens**（游戏行业专项），
其中 **GAMEREL03** 的标题是：

> **How do you persist game state during infrastructure disruptions?**
> （基础设施中断期间，你如何保住游戏状态？）

这正是您的问题，而且 AWS 给的处方比我们本次做的**更根本**。

### 7.2 官方处方：把状态外置，不是在本地盘上存得更勤

GAMEREL03-BP01 原文（`[文档]`）：

> configure your game to continuously perform **asynchronous updates of a player's
> game state to a highly-available cache or database** such as Amazon ElastiCache
> (Redis OSS) or Amazon MemoryDB. If a server failure occurs, the player's last
> saved game state can be fetched from the external data store, and their session
> can be restored on a new game server instance.

**这在很大程度上消解了第 5 章那个风险**：如果玩家状态在 ElastiCache／MemoryDB 里，
根卷 I/O 停滞就不再等于丢档，而且新实例可以直接把会话恢复起来。

### 7.3 官方同时给了第二条路线，适用于快节奏游戏

同一份文档接着说（`[文档]`）：

> may not be suitable for **fast-paced or competitive games** where the state changes
> are so frequent ... that introducing even a performant in-memory cache data store
> would result in **replication lag that is too significant** to be useful to restore
> a session from. For games of this nature, the optimal approach is to **accept the
> loss of the server and send the player back to a game lobby** to find another session.

所以官方认可的是**两条**路线，请按您的游戏类型选：

| 路线 | 做法 | 适用 | 玩家体验 |
|---|---|---|---|
| **A：状态外置** | 异步写高可用缓存／数据库，故障后在新实例上恢复会话 | 状态变更频率与规模允许复制延迟 | 会话可续，感知最小 |
| **B：接受服务器丢失** | 不做外置，故障后把玩家送回大厅重新匹配 | 快节奏／竞技类，复制延迟大到无法用于恢复 | 掉线但几秒内进新局 |

对「一个 EC2 = 一个持久世界」这种形态，AWS 另一篇博客给了四个更贴的状态存储选项：
存档文件直接写 S3、本地库 dump 同步到 S3、状态写 DynamoDB 键值、自建 API 层。

### 7.4 请注意本方案的定位：战术层，不替代架构层

您当前的架构 —— 一个 EC2 一个区服、无高可用、靠云厂商自动恢复 ——
**既没走 A 也没走 B**，它是在赌单台机器不出问题。

所以建议分两个层次，**都要做，且不要互相替代**：

| 层次 | 内容 | 达到的效果 | 时间尺度 |
|---|---|---|---|
| **战术层**（本次交付） | 探测 + 编排，压缩故障到恢复的时间 | 中断从 6–7 分钟降到约 **37 秒** | 数周可落地 |
| **架构层**（GAMEREL03） | 按 A 或 B 改架构 | 单机故障不再等于区服中断 | 需产品与研发排期 |

**必须说清的一点：37 秒仍然是 37 秒的中断。**
路线 A 的目标是玩家会话在新实例上继续，路线 B 的目标是玩家几秒内进入另一局 ——
两者都比「等 37 秒回来」更好。把本次交付讲成「问题解决了」是误导。

诚实的定位是：**战术层让您在架构改造落地之前，先把最坏情况从 7 分钟收敛到半分钟，
并且获得一套能看清故障的观测能力。** 架构改造该排，但不必等它才动手。

## 第 8 章　现成方案调研：能借鉴什么，以及一个反面教材

我们查了公开可用的同类方案，结论是：**基础设施自愈有现成件，
但「判断服务到底还活着吗」这一层没有** —— 那正是本次交付的部分。

### 8.1 架构匹配度最高的现成件：`keirans/aws_autoheal`

它的自述目标原文就是您的架构：

> provide resilience to an application that **cannot autoscale**,
> and to look to make it as robust in a **single AZ** as possible.

做法（单个 CloudFormation 模板）：Auto Scaling 组期望容量 1（不为扩容，
只为「实例挂了自动换一台」）+ 数据卷与 EIP 都与实例解耦 +
生命周期钩子把新实例卡住 + Lambda 给新实例重挂卷和 EIP + 放行钩子。

**可以借鉴的**：

1. 它把「新实例接管旧数据卷与旧 IP」做成了可复制的模式，
   正好补上我们标为「待测」的备机池／卷迁移路线的**编排部分**
2. 它**刻意不给 EC2 实例任何 IAM 角色** —— 所有 AWS 操作都在实例外的 Lambda 里做，
   实例本身没有权限可被滥用。这个安全取舍建议照搬
3. Lambda 里把卷 ID 和 EIP 硬编码为环境变量，配合按资源收紧的 IAM 策略，
   即使代码有问题也只能操作那一个卷

**必须注意的限制**：

- star 数 4，是教学示例不是生产件，单模板结构作者自己也说生产不该这样
- **它只用 EC2 健康检查**。README 自己写道：生产应加应用级健康检查，
  否则只能发现实例死亡、**发现不了应用假活** —— 这正是第 4 章两个实验揭示的问题，
  也正是本方案探测器要占的位置
- 它绕开的仍然是「等实例停下」，**没有回答「从一个无响应实例上摘卷要多久」**

### 8.2 一个反面教材：AWS 官方示例里的告警配置本身很慢

`aws-samples/aws-ec2-statuscheck-failures-logging`（**已于 2026-01 归档为只读**）
做的是把状态检查失败事件送到集中日志做合规审计，不做修复。

它 README 给出的示例告警命令是这样的：

```
--period 300 --evaluation-periods 2
```

**300 秒周期 × 2 个评估点 = 最快 10 分钟才告警。**
叠加我们实测的 84 秒指标发布延迟与 235 秒 AWS 侧检测延迟，
照这个示例配，检测段会落到十几分钟量级。

这条正好从反面印证第 2 章的建议：**不要靠 CloudWatch 告警做检测。**
那个示例的目的是审计留痕而不是快速检测，但很容易被当成推荐配置照抄 ——
**请检查您现有告警是否用了类似的 `period × evaluation-periods` 组合。**

### 8.3 两个便宜的起点工具

| 工具 | 用途 | 对您的价值 |
|---|---|---|
| `hassantahhan/ec2recovery` | 统计账号内有多少 EC2 配了自动恢复告警或在 ASG 里，给出「恢复覆盖率」 | 讨论方案前先量一个数：现有 N 个区服里到底有几台配了恢复。按第 2.4 节的发现，这个覆盖率还要再打折 |
| `aws-samples/amazon-cloudwatch-auto-alarms` | 按 EC2 tag 自动创建标准告警集 | N 个区服逐台建告警不现实，这个能批量做 |

**用批量建告警工具时必须带上 6.1 节的教训**：
批量创建很容易把 `VolumeStalledIOCheck` 这种本环境**零数据点**的指标也一起建进去，
于是得到 N 个永久 `INSUFFICIENT_DATA` 的告警。**批量工具会把一个盲区复制 N 份。**

### 8.4 公开方案里缺失的那一层

搜索没有找到「应用级推进判据 + 分类器 + 对照抑制」这一整套的现成实现。
找到的方案分两类：

- **基础设施层自愈**（ASG／Lambda 重挂卷与 IP）—— 解决「换一台机器」
- **状态检查事件的记录与告警** —— 解决「留痕」

**中间那层缺失的正是本次交付**：判断「这台机器上的服务到底还活着吗」，
以及「这个判断可不可信」。这也解释了为什么现状会停在「等云厂商自动恢复」——
公开方案里确实没有这一层可以直接拿。

## 第 9 章　探测器跑在哪里、由谁执行

这一章回答落地时最先会被问到的三个操作问题。
**其中第一个是常见误解，如果搞错，整套监控会在最需要它的时候失效。**

### 9.1 三句话回答

| 问题 | 回答 |
|---|---|
| 探测程序运行在哪里？ | **必须在被探测实例之外**，绝不能装在区服实例上 |
| 用什么执行？ | 一个**常驻长进程**，由 systemd（EC2）或容器编排（Fargate）拉起 |
| 能用 SSM Agent 做检测吗？ | **不能。** 它跑在被探测实例内部，实例挂了它一起挂 |

### 9.2 SSM 是动作通道，不是检测通道

SSM Agent 是**跑在被探测实例操作系统里**的进程，因此天然继承这台机器的全部故障：

| 故障 | SSM Agent 的表现 | 能否用于检测 |
|---|---|---|
| 内核 panic | 一起死 | 不能 |
| 宿主机故障 | 一起没 | 不能 |
| 根卷 I/O 停滞 | 自身也可能卡在 I/O 上 | 不能 |
| 网络隔离 | 心跳中断，但「静默」与「它自己挂了」分不开 | 不可靠 |
| **游戏进程假活（tick 冻住）** | **Agent 完全正常，报告一切健康** | **不能** |

最后一行是要点：第 4 章实测中游戏进程被冻住后，**连续 12 轮 HTTP 200、TCP 可连，
操作系统层面一切正常** —— 任何跑在这台机器里的 agent 都会报告健康。

**「用带内 agent 检测宿主机故障」在逻辑上不成立**：
需要它报警的时候，它正是坏掉的那个东西。

顺带说明 SSM 的 `PingStatus`（`Online` / `ConnectionLost`）也不能当检测判据 ——
它与 status check 是同类的控制面信号，对「机器在但服务死了」全盲，
而且其判定延迟本次**未测**（`[待测]`）。它只适合事后归因。

### 9.3 SSM 真正的位置：动作阶梯第一档

```
APP_STUCK / APP_DEAD ─► SSM Run Command: systemctl restart <服务>   ← SSM 在这里
                         └─ 超时未就绪 ─► EC2 API: stop(SkipOsShutdown) + start
HOST_DOWN            ─► EC2 API: stop(SkipOsShutdown) + start        ← SSM 用不上
STORAGE_STALLED      ─► EC2 API: stop(SkipOsShutdown) + start        ← SSM 用不上
```

| 层 | 通道 | 前提 | 用途 |
|---|---|---|---|
| 轻动作 | **SSM Run Command**（带内） | OS 还活着 | 只重启服务进程，不动实例，最快 |
| 重动作 | **EC2 控制面 API**（带外） | 只要 API 可达 | OS 已不听话时唯一还能用的手段 |

**所以 SSM 是必要的，但它在动作侧，不在检测侧。**
把两者混在一起，就会做出一个「实例挂了就什么都不知道」的监控系统。

### 9.4 执行方式：三个选项

探测器本质上是个**有状态的长进程** —— 判据是「连续 5 轮失败且已持续 8 秒」，
这个连续计数在进程内存里。

| 方案 | 1 秒级轮询 | 评价 |
|---|---|---|
| 独立 EC2 + systemd | 可以 | **本次实测用的形态** |
| **ECS / Fargate 常驻任务** | 可以 | **生产推荐** |
| Lambda 定时触发 | **不行** | EventBridge 最小 1 分钟；且连续计数得外置到 DynamoDB，每轮读写引入的延迟与失败模式比省下的运维成本更贵 |

推荐 Fargate 是因为它消掉一个循环依赖：
**用 EC2 跑探测器，你就多了一台需要被监控的机器 —— 而它恰好是那台负责监控的机器。**
Fargate 任务挂掉由 ECS 自动重拉。

**该形态属 `[待测]`**：迁过去要验容器网络下 ICMP 是否可用（分类器依赖它）、
以及任务重启后连续计数归零对判定的影响。

### 9.5 「不受被探测实例影响」要切断五类共担故障域

带外不只是「装在另一台机器上」：

| # | 共担故障域 | 后果 | 处置 |
|---|---|---|---|
| 1 | 同一台实例 | 目标死则探测器死 | 绝不同机，这是底线 |
| 2 | **同一个 AZ** | AZ 级事件同时带走两者 | 探测器放在与目标**不同的 AZ** |
| 3 | 同一子网／路由表／NAT | 路由故障看起来像目标挂了 | 跨子网，且 `PROBER_SIDE` 判据要能识别 |
| 4 | 同一存储路径 | 存储事件影响两者 | 探测器不挂业务卷 |
| 5 | 同一套凭证／API 端点 | API 不可达时既看不见也做不了动作 | **无法消除**，见 9.7 |

### 9.6 本次验证在这一点上的局限（必须说明）

实测环境中，探测器与被探测实例**在同一个子网、同一个 AZ（`ap-northeast-1a`）**。

**也就是说上表第 2、3 项本次并未满足** ——
一次真正的 AZ 事件会同时带走探测器和目标，本次验证覆盖不到这种情形。

这是有意的取舍（本次要验的是判据是否成立，不是拓扑是否抗 AZ 故障），
但**生产部署必须把探测器移到另一个 AZ**，且这一点没有实测数据支撑，属 `[待测]`。

### 9.7 控制面依赖去不掉

探测器要发动作，必须能调用 EC2 API。**这个依赖无法消除**：
区域级控制面故障时，本方案与 AWS 自动恢复**同时**失效。

诚实的说法是：**本方案把故障域从「一台实例」缩到「一个区域的控制面」，没有缩到零。**

### 9.8 带外部署带来的新问题，以及它的解法

探测器说「目标不可达」，可能是目标真挂了，也可能是**探测器自己的网络坏了**。
对照实例（sentinel）就是为此存在：

| 目标可达 | 对照可达 | 结论 |
|---|---|---|
| 否 | **是** | 目标真有问题 → 允许动作 |
| 否 | **否** | **探测器侧问题** → 弃权，不动作 |

第 6.2 节已说明：账号里现有 EC2 在原状安全组下**全部不可达**。
若不做这个阳性对照就上线，对照会永远失败 → 每次真实故障都判「探测器侧问题」
→ **得到一个永不动作的恢复系统，而且它看起来在正常运行。**

因此程序把「对照可达」做成**启动硬条件**，不可达就拒绝启动。

### 9.9 存储探测走的是另一条路

存储故障是唯一**完全不碰目标主机**的一条探测通道：走 AWS 控制面
`DescribeVolumeStatus`，由独立线程按较慢间隔轮询，与上面四条探针并行。

之所以必须绕开主机：第 5 章实测根卷 I/O 停 3 分钟而探测器 427 轮全判健康，
而且进程一旦碰到停滞的卷就自己卡在 I/O 里，连报告都发不出来。

**这条通道有一个卷型硬前提（gp2 无效），并且我们在这里犯过一个会造成误动作的错误。**
机制、前提与那个错误都写在 5.5 至 5.7 节，不在这里重复。

### 9.10 谁看着探测器自己

探测器主机一死，所有区服**静默**失去监控，而静默不触发任何告警。
已实现探测器心跳指标（有真实数据点）。

**关键**：这个告警必须配成**「缺数据即报警」**，
不能配成「数值超阈值才报警」—— 探测器死掉的表现是不再发数据，
而 CloudWatch **默认把缺数据当作正常**。

**注意时间尺度。** 这里原先写的是「自定义指标延迟未测，不应假设是秒级」，
**已实测，那句话过于保守**：

| 通道 | 发布延迟 | 等级 |
|---|---|---|
| 自定义指标（心跳走这条） | **0.871 秒**（n=5，0.602–0.942） | `[实测]` |
| AWS 托管 EC2 状态检查指标 | 84 秒 | `[实测]` |

约 **95 倍**差异。**但结论方向不变**：心跳告警仍是**分钟量级兜底**，
不是秒级检测通道 —— 因为瓶颈不在发布延迟，而在**告警评估周期**
（最小 60 秒 × 评估点数）。把 0.871 秒当成「心跳能秒级发现探测器死亡」是错的推论：
**发布快不等于告警快。**

### 9.11 落地清单

| # | 事项 | 状态 |
|---|---|---|
| 1 | 探测器部署在被探测实例之外 | `[实测]` 本次即如此 |
| 2 | 探测器与目标**跨 AZ** | `[待测]`，本次同 AZ 同子网，是已知局限 |
| 3 | 对照实例阳性验证，并作为启动硬条件 | `[实测]` |
| 4 | 探测器心跳 + **缺数据即告警** | 指标 `[实测]`；告警配置待客户侧建 |
| 5 | SSM 只用于轻动作，不用于检测 | 设计已如此 |
| 6 | 迁到 Fargate 常驻任务 | `[待测]` |
| 7 | 多探测器跨 AZ 投票 | 已设计，未实现 |
| 8 | **逐台核实根卷卷型**（gp2 无 `io-performance`，存储旁路失效） | `[实测]` 前提已确认，客户侧需逐台核对 |
| 9 | 用 `set-alarm-state` 演练 reboot/stop/terminate 恢复路径 | `[实测]` 三种均可注入，见 `D10` 报告 |

## 第 10 章　落地方案：分三期

### 第一期：只改检测（收益最大，风险最低）

**目标**：把检测段从 255 秒压到 15 秒量级。不动任何恢复逻辑，纯观测。

| # | 事项 | 责任方 | 说明 |
|---|---|---|---|
| 1.1 | 游戏服暴露健康端点，返回**帧循环推进计数** | **客户应用团队** | 判据是计数在推进，不是 HTTP 200，不是端口可连 |
| 1.2 | 健康端点额外暴露**上次成功存档的时间戳** | **客户应用团队** | 覆盖存储故障盲区，见第 5 章 |
| 1.3 | 部署探测器，1–2 秒间隔 | 客户运维 | 先只告警，不接恢复动作。**部署位置与执行方式见第 9 章** —— 不要装在区服实例上 |
| 1.4 | 配对照实例并**验证其可达** | 客户运维 | 见 6.2 与 9.8 节，这是硬前提 |
| 1.4b | 对照实例要与**被探测的区服**同 AZ 同子网；探测器本身则要与区服**跨 AZ** | 客户运维 | 两者放置方向相反，容易搞混，见下方说明 |
| 1.5 | 旁路信号直接轮询 `DescribeInstanceStatus` 与 `DescribeVolumeStatus` | 客户运维 | 不要等 CloudWatch 告警，实测各快 64 秒和 63 秒 |
| 1.6 | 探测器自身发心跳指标，并建「心跳消失」告警 | 客户运维 | 见下方说明 |

**1.4b 的方向容易搞反，说明一下**：对照实例的作用是回答
「是这台区服坏了，还是探测器的网络坏了」，所以它必须和**区服**在同一个网络邻域
（同 AZ 同子网），这样「区服不可达但对照可达」才能证明问题出在区服身上。
而探测器要避免和区服同时被一次 AZ 事件带走，所以探测器自己要**跨 AZ**。
一句话记：**对照贴着区服放，探测器离着区服放。**

**1.6 值得单独强调**：探测器主机一死，所有区服**静默**失去监控，
而面板上什么都不变。误判至少看得见，这个看不见。
所以「谁看着探测器」这件事的优先级**高于**多探测器投票。
建告警时注意：必须确认它**至少进入过一次 `OK`** 才证明它能取到数据完成评估
—— 永远停在 `INSUFFICIENT_DATA` 的告警等于不存在。

**第一期验收**：跑一次 FIS 演练，确认探测器在 15 秒量级发出告警，
且对照机制被反向验证过（人为让对照失败，确认动作被抑制）。

### 第二期：接上恢复编排

| # | 事项 | 责任方 |
|---|---|---|
| 2.1 | 游戏服实现**周期性检查点 + 启动时校验存档完整性** | **客户应用团队**（硬前提） |
| 2.2 | 编排器停止调用使用 `SkipOsShutdown=True` | 客户运维 |
| 2.3 | 恢复完成判据用「应用可服务」，不用 status check `ok` | 客户运维 |
| 2.4 | 单飞锁 + 冷却期 + 每日上限 | 客户运维 |
| 2.5 | 先 dry-run 跑通动作阶梯，再开 `--apply` | 客户运维 |
| 2.6 | 决定是否关闭 AWS 自动恢复（避免与自建编排相撞） | 客户 + AWS 共同评估 |

**2.1 是 2.2 的前提**：`SkipOsShutdown` 不刷文件系统缓存，
没有周期性检查点就等于用「容忍内存丢失」换来了「丢玩家进度」。

**2.6 说明**：本次实测中两者未相撞，但那是因为 guest 侧故障不激活 AWS 那一侧。
宿主机真故障时的相撞行为**未验证**。若决定自己接管全部恢复，
用 `modify-instance-maintenance-options --auto-recovery disabled` 显式关闭。

**第二期验收**：演练中端到端达到 40 秒量级；反向验证抑制机制
（对照失败时必须不动作）；确认冷却期把重复请求压成一次。

### 第三期：可选优化（不阻塞前两期）

| # | 事项 | 为什么可后补 |
|---|---|---|
| 3.1 | 多探测器投票（quorum） | 误动作已被对照 + 双档阈值压住；且误动作率目前**未测量**，先拿到实际数字再决定是否值这套复杂度 |
| 3.2 | Auto Scaling 组替换 / 备机池 | 原以为必需，是因为误判了停止耗时。实测停止只需 11.5 秒，主路径已够快 |
| 3.3 | 降低 1 秒轮询的 CloudTrail 成本 | 稳态用 5–10 秒（仍远快于 60 秒检查周期），怀疑故障时再切 1 秒 |
| 3.4 | 区分「卷自身受损」与「宿主机-卷可达性」 | 两者动作不同（换宿主机 vs 从快照替换卷），需单独设计用例才能分辨 |

## 第 11 章　需要客户自己做的两件事

交付物里绝大部分是运维侧可直接部署的，但有**两件必须应用团队动手**，
且它们是硬前提，不是加分项：

### 11.1 健康端点暴露两个字段

```json
{
  "tick": 481923,                                  // 主循环推进计数，单调递增
  "last_checkpoint_success_timestamp": 1789636724,  // 上次成功检查点的 Unix 时间戳（秒）
  "players": 812,                                  // 可选，便于运营判断影响面
  "loop_lag_ms": 3.1                               // 可选，用于慢告警
}
```

两个字段各自不可替代：

- **没有 `tick`**：进程冻死时探不到（第 4 章两个实验各连续 6 轮和 12 轮假健康）
- **没有 `last_checkpoint_success_timestamp`**：存储故障期玩家在玩注定丢档的局（第 5 章）

`tick` 的实现原理、阈值怎么定、以及三种会让它静默失效的错误写法，
**见 4.0.1 节** —— 那一节是给实现这个字段的人看的。

第二个字段为什么用**时间戳**而不是「距今多少秒」：让消费方用自己的时钟算差值，
不受采集延迟影响；而且原始时间戳能区分「一直没成功」和「刚刚成功过」。
如果贵司已有实现暴露的是「距今秒数」，探测器**两种都认**，不必为改名返工。

检查点判定有一个实现要点：**落盘必须真的 `fsync`**。
只写进页缓存的话，「检查点成功」在存储故障时会给出**假的成功**，
而那恰恰是要暴露的问题。

### 11.2 周期性检查点 + 启动时校验

`SkipOsShutdown` 路径上没有优雅关机，不会帮您刷文件系统缓存。
落盘周期决定了单次故障最多丢多少进度，这是一个**产品决策**
（玩家能接受丢多少），应该由业务定，然后据此设落盘周期与探测阈值。

## 第 12 章　我们做不到的部分（诚实边界）

这一章列出本次**无法验证**的内容。列出来是为了让您知道哪些结论不能引用。

### 12.1 宿主机侧故障那一整档全部未验证

您抱怨的 system status check 失败 = **宿主机侧问题**（掉电、物理机故障、
网络可达性）。这一档**注入不了**：

- AWS FIS 没有对应的故障动作
- system status check 测的是宿主机侧，guest 内做任何事都影响不到它
- 强制告警进 ALARM 也触发不了恢复动作（见 6.4 节）

因此下列四件事**只能等一次真实故障才能测**：

1. AWS 侧对宿主机故障的检测延迟（是否也是 235 秒量级）
2. AWS 自动恢复自身的恢复段耗时（您观测的 6–7 分钟里，这一段占多少）
3. `SkipOsShutdown` 在宿主机不可达时是否同样有效（本次的 11.5 秒是宿主机健康、guest 挂死的场景）
4. 自建编排与 AWS 自动恢复的真实相撞行为

**本次所有恢复段数字都来自 guest 内 kernel panic，与您抱怨的那一档不是同一个故障域。**
这不是方案的缺陷，是可注入性的边界。

### 12.2 对应的动作：现在就把取证器部署起来

既然那一档只能等真实事件，就必须在事件发生时**已经在记录**。

我们交付了一个常驻取证器，它的核心设计是**把三个时间轴分开记**：

| 时间 | 含义 |
|---|---|
| `t_fault` | 故障真正发生的时刻 |
| `t_datapoint` | 指标数据点自己声明的时间戳 |
| `t_observed` | 我们第一次能看到它的时刻 |

`t_datapoint − t_fault` 是 AWS 侧检测延迟，`t_observed − t_datapoint` 是指标发布延迟。
混用任意两个都会算出错误的分段耗时。

**下一次真实宿主机故障后，这个取证器能给出精确的分段耗时表。
拿这张表去跟 AWS 服务团队谈「报得太慢」，比「观察下来 6-7 分钟」
有说服力得多 —— 因为它能指出慢在哪一段。**

### 12.3 其它已知未验证项

| 项 | 状态 |
|---|---|
| ~~`reboot`/`stop`/`terminate` 三种告警动作~~ | **已测，三种都会真的执行**，见 3.8 与 6.4 |
| Auto Scaling 组替换的实际恢复段耗时 | 未测 |
| 备机池 + 卷迁移方案 | 未测。注意它绕开了「等实例停下」，但没绕开「从无响应实例上摘卷」，两者可能是同一个物理约束 |
| 多探测器投票 | 未实现（设计文档已出，见交付物清单） |
