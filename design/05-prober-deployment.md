# 探测器跑在哪里、由谁执行、如何不与被探测实例共命运

本文回答三个操作层面的问题。原方案文档只给了一张拓扑表，
没写清「谁来跑这个进程」，评审时被问到，补这一份。

---

## 一、一句话回答

| 问题 | 回答 |
|---|---|
| 探测程序运行在哪里？ | **必须在被探测实例之外**，绝不能装在区服实例上 |
| 用什么执行？ | 探测器是一个**常驻长进程**，由 systemd（EC2）或容器编排（Fargate）拉起 |
| 能用 SSM Agent 吗？ | **不能用于检测。** SSM Agent 跑在被探测实例内部，实例挂了它一起挂 |
| 怎么不受被探测实例状态影响？ | 带外部署 + 跨 AZ + 切断五类共担故障域 + 有人看着探测器自己 |

---

## 二、SSM 的定位：它是动作通道，不是检测通道

这是最容易搞错的一点，值得单独说清。

### 2.1 为什么 SSM 不能做检测

SSM Agent（`amazon-ssm-agent`）是**跑在被探测实例操作系统里**的一个进程。
于是它天然继承了被探测实例的全部故障：

| 故障 | SSM Agent 的表现 | 能否用于检测 |
|---|---|---|
| 内核 panic | 一起死 | 不能 |
| 宿主机故障 | 一起没 | 不能 |
| 根卷 I/O 停滞 | 自身也可能卡在 I/O 上 | 不能 |
| 网络隔离 | 心跳中断，但**「静默」与「它自己挂了」分不开** | 不可靠 |
| 游戏进程假活（tick 冻住） | Agent 完全正常，报告一切健康 | **不能** —— 这恰恰是最需要检测的那类故障 |

最后一行是关键：D5 实测中游戏进程被 `SIGSTOP` 冻住后，
连续 12 轮 HTTP 200、TCP 可连，**操作系统层面一切正常**。
任何跑在这台机器里的 agent 都会报告健康。

**「用带内 agent 检测宿主机故障」在逻辑上是不成立的** ——
需要它报警的时候，它正是坏掉的那个东西。

### 2.2 SSM Agent 自己的心跳能用吗

SSM 有一个 `PingStatus`（`Online` / `ConnectionLost` / `Inactive`），
理论上可以当作存活信号。**但有两个问题**：

1. **延迟未测**。SSM 心跳间隔与判定 `ConnectionLost` 的阈值是分钟量级，
   本次**没有实测**，属 `[待测]`。按数量级估计它与 status check 同档，
   也就是我们要绕开的那一档，不是要依赖的那一档
2. **它和 status check 是同类信号** —— 都是控制面视角的「这台机器还在吗」，
   对「机器在但服务死了」全盲

结论：`PingStatus` 可以作为**归因用的辅助信息**，不能作为检测判据。

**顺带一条 D10 实测结论**：`set-alarm-state` 强制告警进 `ALARM` 时，
`reboot` / `stop` / `terminate` 三种告警动作**都会真的执行**
（reboot 约 t+26 s，stop / terminate 均 t+1 s 起状态转换），只有 `recover` 是空操作。
这意味着这三条恢复路径可以低成本反复演练，不需要 FIS；
但也意味着**在挂了这些动作的生产告警上做「测一下通不通」会真的停掉或销毁实例**，
演练前必须 `disable-alarm-actions` 或改用一次性实例。

### 2.3 SSM 真正的用处：执行动作阶梯的第一档

```
APP_STUCK / APP_DEAD  ──► SSM Run Command: systemctl restart <service>   ← SSM 在这里
                           └─ 超时未 app ready ──► EC2 API: stop(SkipOsShutdown) + start
HOST_DOWN             ──► EC2 API: stop(SkipOsShutdown) + start          ← SSM 用不上
STORAGE_STALLED       ──► EC2 API: stop(SkipOsShutdown) + start          ← SSM 用不上
```

分工是清楚的：

| 层 | 通道 | 前提 | 用途 |
|---|---|---|---|
| 轻动作 | **SSM Run Command**（带内） | OS 还活着 | 只重启服务进程，不动实例，最快 |
| 重动作 | **EC2 控制面 API**（带外） | 只要 API 可达 | OS 已经不听话时唯一还能用的手段 |

**所以 SSM 是必要的，但它在动作侧，不在检测侧。**
把这两件事混在一起，就会做出一个「实例挂了就什么都不知道」的监控系统。

## 三、探测器跑在哪里：三个选项

### 3.1 选项对比

| 方案 | 1 秒级轮询 | 连续计数状态 | 谁维护它 | 评价 |
|---|---|---|---|---|
| **独立 EC2 + systemd** | 可以 | 进程内存里，天然连续 | 你要给它打补丁、看它死没死 | **本次实测用的形态** |
| **ECS / Fargate 常驻任务** | 可以 | 同上 | 无实例可维护，任务挂了编排层自动重拉 | **生产推荐** |
| Lambda 定时触发 | **不行** | **不行** | 无 | 见下方说明 |

### 3.2 为什么 Lambda 不适合做这个探测器

两个硬问题：

1. **调度粒度**。EventBridge 最小 1 分钟。要做 1 秒轮询只能让单次调用内部循环 60 秒，
   于是变成「用 Lambda 模拟常驻进程」，还要处理跨调用的边界
2. **连续失败计数是有状态的**。判据是「连续 5 轮失败且已持续 8 秒」，
   这个 streak 计数在 Lambda 的无状态模型里必须外置到 DynamoDB 之类，
   每轮读写，**引入的延迟和失败模式比它省下的运维成本更贵**

探测器本质上是个有状态的长进程，硬塞进无状态模型不划算。

### 3.3 推荐形态：Fargate 常驻任务

理由是它消掉了一个循环依赖：**「谁给探测器主机打补丁、谁发现探测器主机挂了」**。
用 EC2 跑探测器，你就多了一台需要被监控的机器 —— 而它恰好是那个负责监控的机器。

Fargate 任务挂掉由 ECS 自动重拉，`desiredCount` 保证副本数，跨 AZ 分布由服务定义控制。

**注意**：本次验证**用的是 EC2 + 手工拉起进程**，Fargate 形态属 `[待测]`。
迁过去要验的是：容器网络下 ICMP 是否可用（分类器依赖它）、以及任务重启后
streak 计数归零对判定的影响。

## 四、如何不与被探测实例共命运：五类共担故障域

「带外」不只是「装在另一台机器上」。要逐项切断下列共担：

| # | 共担故障域 | 后果 | 处置 |
|---|---|---|---|
| 1 | **同一台实例** | 目标死则探测器死 | 绝不同机。这是底线 |
| 2 | **同一个 AZ** | AZ 级事件同时带走两者 | 探测器放在**与目标不同的 AZ** |
| 3 | **同一个子网 / 路由表 / NAT** | 路由或 NAT 故障看起来像目标挂了 | 跨子网；且 `PROBER_SIDE` 判据要能识别 |
| 4 | **同一个 EBS / 存储路径** | 存储事件影响两者 | 探测器不挂业务卷 |
| 5 | **同一套凭证 / API 端点** | API 不可达时探测器既看不见也做不了动作 | 见下方 4.3 |

### 4.1 本次验证在这一点上的实际状况（必须承认的局限）

实测环境中，探测器（`i-PROBER00000000000` / 203.0.113.10）与被探测实例
**在同一个子网 `subnet-EXAMPLE0000001`、同一个 AZ `ap-northeast-1a`**。

也就是说：**上表第 2、3 项本次并未满足。**
一次真正的 AZ 事件会同时带走探测器和目标，本次验证覆盖不到这种情形。

这是有意的取舍 —— 本次要验的是判据是否成立，不是拓扑是否抗 AZ 故障 ——
但生产部署**必须**把探测器移到另一个 AZ，且这一点没有实测数据支撑，属 `[待测]`。

### 4.2 sentinel 对照解决的正是「到底谁坏了」

带外部署带来一个新问题：探测器说「目标不可达」，
可能是目标真挂了，也可能是**探测器自己的网络坏了**。

对照实例（sentinel）就是为此存在的：同 AZ 同子网、长期零流量的另一台机器。

| 目标可达 | sentinel 可达 | 结论 |
|---|---|---|
| 否 | **是** | 目标真的有问题 → 允许动作 |
| 否 | **否** | **探测器侧问题** → 判 `PROBER_SIDE`，弃权不动作 |

D6 反向验证过：sentinel 不可达时 12/12 判 `PROBER_SIDE`、升级封顶 soft、
`action_request` 计数 0 —— 也就是说探测器侧故障**不会**被放大成一次区服重启。

而且 `--require-sentinel-up` 默认开、不可达就 exit 3 拒绝启动，
因为实测发现账号里现有 EC2 在原状安全组下**全部不可达**：
如果不做这个阳性对照就上线，sentinel 会永远失败 → 每次真实故障都判 `PROBER_SIDE`
→ **一个永不动作的恢复系统，而且看起来在正常运行。**

### 4.2b 存储旁路有一个卷型硬前提

带外的存储判据依赖 `DescribeVolumeStatus` 的 `io-performance` 项，
而它**仅 `io1` / `io2` / `gp3` 卷支持**；`gp2` 卷返回 `not-applicable`，
这条通道对该卷完全失效（`[实测]` D10）。

代码已按此在启动时预检卷型并在全不支持时拒绝启用该旁路 ——
早期版本判「不等于 `normal` 即故障」，会把 `not-applicable` 当成停滞，
**对每个 gp2 卷触发一次 stop/start**，而日志显示「检测到存储停滞」，外观完全正常。

### 4.3 关于第 5 项：控制面依赖无法消除

探测器要发动作，必须能调用 EC2 API。**这个依赖去不掉**，只能承认：

- 区域级控制面故障时，本方案与 auto recovery **同时**失效
- 这一项在客户视角复核里被列为「无法消除的前提」，不是可以后补的缺口

诚实的说法是：本方案把故障域从「一台实例」缩到「一个区域的控制面」，
没有缩到零。

## 五、谁看着探测器自己

这是客户视角复核中判定的**最高优先级缺口** ——
比多探测器投票更优先，因为探测器主机一死，所有区服**静默**失去监控，
而「静默」不会触发任何告警。

已实现并验证（`ProberHeartbeat` / `ShardUnhealthy` 自定义指标有真实数据点）：

| 指标 | 语义 | 告警方式 |
|---|---|---|
| `ProberHeartbeat` | 探测器每轮 +1 | **数据点消失即告警**（treat missing data as breaching） |
| `ShardUnhealthy` | 当前判为异常的区服数 | 阈值告警 |

关键点：这个告警必须配成**「缺数据即报警」**，不是「数值超阈值才报警」。
探测器死掉的表现是不再发数据，而 CloudWatch 默认把缺数据当作正常。

**注意时间尺度。** 这里原先写的是「自定义指标的这一段本次未测，属 `[待测]`，
**但不应假设是秒级**」——**已实测，那个提醒方向下错了**：

| 通道 | 发布延迟 | 等级 |
|---|---|---|
| 自定义指标（心跳走这条） | **0.871 s**（n=5，范围 0.602–0.942） | `[实测]` |
| AWS 托管 EC2 状态检查指标 | 84 s | `[实测]` |

约 **95 倍**差异。自定义指标就是亚秒级，比我当时保守估计的快得多。

**但结论方向不变**：心跳告警仍是**兜底**（分钟量级发现「监控没了」），
不是检测通道（秒级发现「区服挂了」）。原因换了：瓶颈不在发布延迟，
而在**告警评估周期**（最小 60 秒 × 评估点数）。
把 0.871 秒当成「心跳能秒级发现探测器死亡」是错的推论 ——
**发布快不等于告警快。**

测量方法上还有一个教训：第一次用 1 秒轮询间隔测，三次结果都是 1.046–1.048 秒，
整齐得可疑；查轮询计数发现全是第二次轮询才看到，**那个「1.0 秒」是采样间隔本身**。
改 0.1 秒粒度才拿到真实值。数字整齐到等于自己的采样参数时，先怀疑测量方法。
详见 `validation/reports/D10-metric-latency-volume-type-alarm-actions.md`。

## 六、一个值得考虑的反向形态：死人开关

上面讲的是「探测器主动去探」。反方向的做法是
**让游戏服自己往外推心跳，外部只判断心跳有没有断**（dead man's switch）。

| | 主动探测（本方案） | 死人开关 |
|---|---|---|
| 网络方向 | 探测器 → 目标，需入站规则 | 目标 → 外部，无需入站规则 |
| 检测延迟 | **实测 3.5 秒** | 受传输通道限制，走 CloudWatch 则是分钟量级 |
| 假活检测 | 强 —— 可直接读 tick 是否推进 | 取决于推送方自己判断，**推送逻辑与业务逻辑可能一起冻住** |
| 「静默」歧义 | sentinel 对照可区分 | 网络断与进程死**分不开** |

**推荐组合而不是二选一**：主动探测做秒级检测，死人开关做兜底
（万一探测器整个体系失效，至少心跳消失能报出来）。

需要注意死人开关的一个陷阱：如果推送心跳的代码和游戏主循环在同一个线程里，
主循环冻住时心跳也停 —— 那是好事（能检测到）；
但如果心跳在独立线程里，主循环冻死而心跳照发 —— 就变成了另一个假活源。
**这正是 D5 实测里 tick 判据存在的理由：判据必须是业务进度本身在推进。**
