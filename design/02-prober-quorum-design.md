# 探测器 Quorum —— 设计文档

状态：**设计，未实现**。本文只定设计与验收判据，不含代码。
前置阅读：`01-prober-and-orchestration.md`（判据表、sentinel 对照、双档阈值、动作阶梯）。

---

## 1. 它解决什么问题，以及不解决什么

恢复动作是破坏性的：`stop/start` 会把一个区服上所有在线玩家踢下线。
单个探测器自身的局部网络问题若能独立触发动作，代价就是一整个区服白重启。

Quorum = **部署 N 个探测器，只有至少 M 个独立判定同一区服故障，才允许动作**（下文取 N=3、M=2）。

### 现有机制已经覆盖的部分

| 机制 | 覆盖的误判形态 | 验证 |
|---|---|---|
| sentinel 对照 | 探测器自身网络整体坏了 → 判 `PROBER_SIDE` 抑制动作 | D6 反向验证；D9 一次真实生效 |
| 双档阈值（连续 5 次 **且** 已持续 ≥8 s） | 8 秒以内的瞬时抖动 | D5/D5b/D1 实测 |
| 冷却期 + 每日上限 | 一次故障被放大成一串重启 | D5 实测 12 次请求被压成 1 次 |

### Quorum 补的是这几道闸之间那条缝

**只影响「某一个探测器 ↔ 某一个区服」这一条路径、持续超过 8 秒、
而该探测器同时还能正常访问 sentinel** 的故障。具体形态：

- 探测器 ENI 的 conntrack 表项耗尽，只影响那一个五元组
- 安全组／NACL 变更只挡住某一个来源到区服端口（D6 就是人为制造的这种）
- 单 AZ 内的非对称路由或某一条坏路径
- 区服 ENI 出问题，对部分对端可达、对部分不可达

这类故障不常见，但它恰好能绕过现有全部三道闸 —— 这是 quorum 存在的唯一理由。
**它不提高检测速度，也不提高检测灵敏度，只降低误动作率。**

## 2. 实现路径选择

| 方案 | 做法 | 取舍 |
|---|---|---|
| **编排器侧计票**（推荐） | 探测器只上报判定，编排器计票后再动作 | 编排器**已经**是唯一动作方且带单飞锁与冷却期，不引入新组件；探测器改动最小 |
| 共享存储 | 探测器把判定带 TTL 写 DynamoDB／Redis，动作方读全部票 | 探测器之间彻底解耦，但多一个依赖与一套 IAM |
| 探测器互探 | 每个探测器暴露端点报自身判定，动作方轮询其余 | 无中心组件，但 N 个探测器 N² 条连接，且新增一批**本身需要被探测**的路径，与要解决的问题同源 |

**选编排器侧计票。** 理由是它复用了已有的唯一动作点：
`recovery_orchestrator.py` 现在就是被 `--on-hard` 调起的短命进程，
已有 `O_EXCL` 单飞锁与落盘的冷却历史，计票只是在闸门链上再加一环。

## 3. 数据模型

每个探测器在判定为可动作档（`hard`）时，不再直接调编排器执行，
而是**投一票**；票落在编排器可读的位置（沿用现有 `--state-dir` 的落盘约定）：

```
vote-<shard_instance_id>-<prober_id>.json
{
  "prober_id":   "prober-a",                  // 稳定标识，不用 hostname（重建即变）
  "shard":       "i-REDACTED00000000002",
  "verdict":     "HOST_DOWN",
  "reason":      "icmp+tcp down, sentinel healthy",
  "ts":          1789630796.123,              // 投票时刻（墙钟）
  "held_s":      12.04,                       // 该判定已持续多久
  "sentinel_ok": true                         // 该探测器自己的对照结论
}
```

`prober_id` 必须是配置给定的稳定标识。**不要用 hostname** ——
探测器实例重建后 hostname 变了，旧票会被当成另一个探测器的票，
这正是「身份不唯一」那一类缺陷（本项目已踩过三次）。

## 4. 计票规则（四条，每条都有必须如此的理由）

### 4.1 票必须新鲜，过期票不计

`vote_ttl`（建议 = 探测器 `hard` 阈值时长的 3 倍，需按客户实际值推导）。

**这是正确性要求，不是优化。** 反例：探测器 A 投了 `HOST_DOWN` 后进程死掉，
它的票永久留在存储里；此后只要**任何一个**其它探测器出一次假阳性，
1 张陈旧票 + 1 张新票就凑成 2/3，quorum 被绕过。
陈旧票必须过期，否则「探测器死亡」会变成「误动作放大器」。

### 4.2 分母是配置的期望探测器数，不是当前活着的数量

`--expected-probers 3 --quorum 2`，判据是**绝对票数 ≥ 2**。

**绝不能用「活着的探测器数」做分母。** 反例：三个探测器挂了两个，
剩下一个算 1/1 = 100%，于是它可以独自动作 —— quorum 形同不存在，
而且恰好发生在系统最不健康、最该谨慎的时候。

### 4.3 `PROBER_SIDE` 票不是否决票，只是弃权

一个探测器报 `PROBER_SIDE` 表示**它自己**那条路坏了，
这正是应该依赖其余探测器的时刻，所以它不否决，只是不计入赞成票。

但要加一条兜底：**若报 `PROBER_SIDE` 的探测器数量 ≥ 期望数 − 赞成阈值 + 1**
（N=3、M=2 时即 ≥ 2 个弃权），则局面过于混浊，不动作并升级告警。
这一条防止「三个里两个自称路坏了，剩下一个说区服死了」这种没法判断的情形被当成有效判定。

### 4.4 Quorum 只适用于「路径相关」的判定

| 判定 | 来源 | 是否需要 quorum |
|---|---|---|
| `HOST_DOWN` | 探测器→区服的 ICMP/TCP | **需要**，完全依赖网络路径 |
| `APP_STUCK` / `APP_DEAD` | 探测器→区服的 HTTP/TCP | **需要**，同上 |
| `STORAGE_STALLED` | `DescribeVolumeStatus`（AWS 控制面） | **不需要**。所有探测器查的是同一个控制面视图，票必然一致；要求 quorum 只会在「只有一个探测器配了 `--volume-ids`」时白白阻塞动作 |
| `CHECKPOINT_LAGGING` | 游戏服自报的检查点时间戳 | 不适用 —— 该判定本就刻意不可动作 |
| `PROBER_SIDE` / `UNKNOWN` | — | 不适用 —— 本就不可动作 |

这条区分容易被漏掉：**把 quorum 一律套到所有判定上，会让存储故障这条
本来就靠旁路信号才看得见的路径变得更难触发。**

## 5. 退化行为：票不可读时怎么办

这是本设计里唯一一个真正的权衡，两端都不可接受：

| 选择 | 后果 |
|---|---|
| fail open（读不到票就照常动作） | quorum 形同不存在，等于没做 |
| fail closed（读不到票就永不动作） | 汇票通路一挂，**全部区服的自愈同时静默失效**，而面板上一切正常 |

fail closed 就是 sentinel 那个坑的同款 ——「门禁在结构上永不触发，比没有门禁更危险」。
而且它与客户的核心诉求（恢复要快）直接冲突：等人来看，就回到了分钟级甚至更久。

### 建议：有界降级，而不是断崖

1. 默认 **fail closed**：读不到票 → 不动作 → 立即告警（复用探测器心跳那套自定义指标）。
2. 但设一个 `--solo-action-after`（**远大于**正常 `hard` 阈值，
   建议为其 3–5 倍，具体值须从客户自己的历史分布推导，不要拍整数）：
   同一个探测器持续持有可动作判定超过该时长、且期间始终读不到其它票，
   则**允许单票动作**，并在动作记录里显式标注 `quorum=bypassed` 与绕过原因。
3. 绕过必须计入每日上限，且触发一条独立告警 —— 它是异常路径，不能安静地成为常态。

这样把「静默永不动作」换成「更慢但仍然自动，且留下审计痕迹」。

## 6. 与现有闸门的顺序

计票插在探测器与编排器之间，其余闸门位置不变：

```
探测器判定 hard
   └─> 投票（写 vote 文件）
        └─> 编排器被唤起
             ├─ 1. 计票：新鲜票 ≥ M ？（4.1–4.4）        ← 本设计新增
             ├─ 2. 冷却期与每日上限                        （已有）
             ├─ 3. 单飞锁（O_EXCL + PID 存活校验）          （已有）
             ├─ 4. auto recovery race 检查                  （已有）
             └─ 5. 按判定走动作阶梯                          （已有）
```

计票放在最前面：它是最便宜的检查，且失败时不需要拿锁。

## 7. 部署形态

| 项 | 建议 | 理由 |
|---|---|---|
| 探测器数量 | 3 | 2/3 能容忍 1 个探测器出问题；2 个探测器无法形成多数 |
| 放置 | **跨 AZ**，不与任何被测区服同 AZ 全部堆放 | 单 AZ 事件不应同时带走全部探测器 |
| sentinel | 每个探测器各自配同 AZ 同子网的对照 | 对照必须与被测目标共享故障域才有意义 |
| 心跳 | 每个探测器都发，维度含 `ProberHost` | 死掉的探测器必须能被单独识别出来，否则 4.1 的陈旧票问题无从排查 |

## 8. 验收判据（做完必须跑的四个用例）

沿用「注入真缺陷必须被抓到」的要求，四个都要，缺一个这套闸门就不算验过。

### Q1 —— 单探测器假阳性被压制（正向）
只收回**一个**探测器 SG 到区服端口的入站规则，其余两个保持可达。
**判据**：该探测器判 `HOST_DOWN` 并投票，另两个投 `HEALTHY`（或不投），
票数 1 < 2，**无动作**，并记一条「quorum 未达成」。

### Q2 —— quorum 非空转（反向，最容易被忽略）
收回**两个**探测器的入站规则。
**判据**：票数 2 ≥ 2，动作**必须**触发。
不做这一条，就无法区分「quorum 正确地压制了误判」与「quorum 永远达不成」。

### Q3 —— 陈旧票不计（正确性）
让探测器 A 投 `HOST_DOWN` 后立刻杀掉它；等超过 `vote_ttl` 后，
再让 B 单独投一票 `HOST_DOWN`。
**判据**：**无动作**。若动作触发，说明 A 的陈旧票被计入，
「探测器死亡」变成了「误动作放大器」，必须先修。

### Q4 —— 汇票不可用时的降级行为符合选定档位
让编排器读不到票（如把 `--state-dir` 置为不可读）。
**判据**：默认 fail closed 时 → 无动作 + 告警；
配了 `--solo-action-after` 时 → 在该时长内无动作、超过后单票动作
且记录 `quorum=bypassed`。两种配置都要各跑一次。

## 9. 明确未决的问题

| # | 问题 | 现状 |
|---|---|---|
| 1 | `vote_ttl` 与 `--solo-action-after` 的具体取值 | 必须从客户自己的探测历史分布推导（正常判定持续时长的分布），本文只给倍数关系，不给数字 |
| 2 | 编排器侧计票要求探测器与编排器共享一个可写位置 | 单机多探测器可用同一 `--state-dir`；跨主机需要共享存储（EFS／DynamoDB），届时方案 2 可能反而更简单 |
| 3 | 那类「只影响单条路径」的故障在真实环境的发生率 | 未知。若实测发现极低，quorum 的收益可能不值这套复杂度，应如实重估而不是因为已经设计了就实现 |
| 4 | 多探测器同时投票时的时钟偏差 | 票用墙钟时间戳，跨主机需确认 NTP 同步；偏差大于 `vote_ttl` 的一小部分即会误判新鲜度 |

第 3 条值得单独强调：**本文档描述的是一个降低误动作率的机制，
而误动作率目前是未测量的。** 在拿到「单探测器方案实际误动作了多少次」
这个数字之前，quorum 的优先级应保持在「可后补」而不是「必做」，
这与 `validation/reports/00-summary.md` 第四点五节的判定一致。
